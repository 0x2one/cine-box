# 映盒剧场 · 迭代待办计划

> 基线版本：v1.1.0（2026-11-26）
> 盘点范围：`src/main`、`src/preload`、`src/renderer`、`src/lanweb`、`docs/`
> 估时口径：单人工作日，含自测，不含发版、联调与跨平台验证
> 维护方式：完成一项就把「任务总表」的状态改成 `已完成`（详情里保留验收记录），并在「实施记录」补一行（日期 / 版本 / 备注）
> 任务 ID（A-01、B-05…）可以直接作为 issue / 提交前缀，例如 `feat(watch): A-01 观看进度存储层`

## 0. 一页结论

- 主链路（采集 → 索引 → 推荐 / 找片看 / 搜索 → 播放 → 缓存 / 导出 → 局域网 → 备份）已经闭环，
  继续堆同类功能收益递减。
- 下一阶段只做三件事：**让用户第二次打开（观看数据）**、**让片库能被找到和信任（元数据 / 检索 / 治理）**、
  **让迭代不翻车（测试 / 契约 / 安全）**。
- 节奏：v1.2 看得下去 → v1.3 看得舒服 → v1.4 找得到 → v1.5 稳得住 → v2.0 多端与收口。
- 明确不做：多语言、插件系统、账号 / 云同步、公开源聚合、全量实时转码、弹幕社交。

## 1. 盘点结论（为什么是这些任务）

### 1.1 已经完成，不再重复投入

站点 XML / JSON 采集、全量 / 增量 / 检索三模式、定时计划与断点续采、跨站同名合并、详情文件缓存、
两级分类与绑定、推荐配置（海报 / 轨道 / 搜索推荐）、独立播放窗（ArtPlayer + hls.js）、
离线缓存（暂停 / 续传 / 转 MP4）、局域网影院与代理、封面多来源回退、备份恢复、应用内更新。

### 1.2 三个结构性缺口

| 缺口               | 代码证据                                                                                     | 影响                                                     |
| ------------------ | -------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| 没有观看数据       | 全库没有 `position` / `history` / `favorite` 的 IPC 或表；`PlayerOpenInput` 没有 `startTime` | 不能续播、不能「继续观看」、不能追剧                     |
| 索引里没有内容维度 | `videos` 只有 name / note / actor / class；年份、地区、语言、导演只在详情 JSON               | 不能按年份 / 地区 / 演员筛选排序，列表只能按更新时间倒序 |
| 搜索只认片名       | `makeSearchText(primaryName)`；本地结果按 `latest_ts` 排序                                   | 搜主演、搜类型、搜备注无结果；精确命中可能被压在后面     |

补充：播放器「数据比 UI 多」——下载侧已经会拉 `EXT-X-MEDIA` 的音轨 / 字幕轨，
但播放器没有字幕 / 音轨入口，截图也关着。

### 1.3 四个容易被忽略的机会点

1. **数据已有、UI 没有**：缓存包里的字幕 / 音轨、详情里的年份 / 地区 / 导演、`detail_accessed_at` 的访问时间。
2. **清缓存会重建缓存库**：`videos:clear` 会删库重建，视频 id 会变；任何跨版本保留的数据
   （收藏、历史、片单）必须用稳定的 `name_key` 做键，不能只用 videoId。
3. **文档自身 backlog**：`docs/视频缓存设计.md` 的 19.2 / 19.3 已经列出搜索范围、缓存上限、
   cron、多计划等待确认项，说明这些不是拍脑袋。
4. **局域网是差异化，但没有鉴权**：目前只适合可信家庭网络，多端叙事缺一块门槛。

## 4. 任务详情

约定：每条都写「目标 / 做法 / 验收 / 风险」。做法只写关键落点，不写完整实现。

### Epic A：观看闭环

#### A-01 观看进度存储层

> P0 · 2 人日 · v1.2 · 依赖：无

- **目标**：有一个稳定的地方存「谁看到第几集第几秒」，清缓存、恢复备份、换版本都不丢、不错位。
- **做法**：
  - 新建 `src/main/watch-store.ts`，复用 `src/main/database.ts` 的业务库连接（`cine-box.db`），
    不要放缓存库——`videos:clear` 会重建缓存库。
  - 表按「每集一行」存，既能算「继续观看」，也能给剧集面板画进度：
    ```sql
    CREATE TABLE IF NOT EXISTS playback_progress (
      video_key TEXT NOT NULL,        -- makeNameKey(片名)，跨缓存重建稳定
      video_id INTEGER NOT NULL,      -- 最后一次见到的缓存 id，仅用于加速
      source_id INTEGER NOT NULL,
      line_index INTEGER NOT NULL,
      episode_index INTEGER NOT NULL,
      episode_name TEXT NOT NULL DEFAULT '',
      position REAL NOT NULL DEFAULT 0,
      duration REAL NOT NULL DEFAULT 0,
      finished INTEGER NOT NULL DEFAULT 0,
      updated_at TEXT NOT NULL,
      PRIMARY KEY (video_key, source_id, line_index, episode_index)
    );
    CREATE INDEX IF NOT EXISTS idx_playback_progress_updated
      ON playback_progress (updated_at DESC);
    ```
  - 主进程收到 `videoId` 后先查缓存库拿 `name_key`；查不到（缓存不可用 / 视频已删）直接返回 `VIDEO_MISSING`，不写脏数据。
  - 上限保护：单库最多保留 5000 行，写入后按 `updated_at` 淘汰最旧；`watch:clear` 支持单部 / 全部。
  - 进度**不进备份**（设备本地数据，不随备份文件跨机器走；`backup:restore` 只清它的五张业务表，不会动进度）；收藏进备份。
- **验收**：
  - 单测覆盖：写入 / 覆盖 / 淘汰 / 清空 / 非法入参。
  - 写入耗时 < 5ms（10 万视频库、5000 行进度）。
  - 删掉 `video-cache.db` 重建后，历史按 `video_key` 仍能匹配回新 id。
- **风险**：业务库的 `init()` 分散在多个 store，新增表要确认启动顺序；备份恢复会 `DELETE` 五张表，别把进度表误加进去。

#### A-02 播放页进度上报

> P0 · 1.5 人日 · v1.2 · 依赖：A-01

- **目标**：播放中不打扰，但关窗 / 切集 / 暂停后进度是最新的。
- **做法**：
  - 在 `PlayerSession` 里订阅 ArtPlayer 的 `video:timeupdate`（10 秒节流）、`video:pause`、`video:ended`、切集和卸载时上报。
  - 上报载荷：`videoId / sourceId / lineIndex / episodeIndex / episodeName / position / duration`；
    `position >= duration - 20` 视为看完（`finished = 1`），下次从 0 开始。
  - 本机文件（下载中心，`fileUrl`）也上报，但没有 `videoId` 时按 `fileName` 生成临时 key 或直接跳过（建议跳过）。
  - 关窗最后一下用 `pagehide` 同步发一次（`ipcRenderer.send`，不等返回）：
    `watch:progress` 同时注册 `handle`（常规）与 `on`（fire-and-forget）。
  - 主进程对同一 key 做 2 秒合并，避免暂停 / 拖动连续写盘。
- **验收**：
  - 播 15 秒关窗，重开显示续播；暂停 / 拖动后立即关窗也不丢。
  - 同时开两个播放窗时互不覆盖（按 `video_key + 集` 区分）。
  - 播放页关闭后主进程无残留定时器。
- **风险**：`player:load` 复用同一窗口时，旧会话的卸载上报可能晚于新会话，必须带 `token`，主进程丢弃过期 token 的上报。

#### A-03 续播

> P0 · 2 人日 · v1.2 · 依赖：A-01、A-02

- **目标**：从「继续观看」进来直接接着看，并明确告诉用户；其它入口默认从头播，设置里可以改成总是续播。
- **做法**：
  - `PlayerOpenInput` / `PlayerPayload` 增加 `startTime?: number`，`player-window.ts` 校验有限正数后转交。
  - 播放页在 `loadedmetadata` 后 seek；`startTime < 5` 或 `> duration - 10` 时不跳。
  - 起播后 `notice('已从 12:34 继续播放')`，并在右上角 chip 提供「从头播放」。
  - 设置 › 播放新增「打开视频时自动续播」开关（`autoResume`，**默认关**）：
    `Settings.tsx` 的 `SettingsSection` 增加 `playback` 分区，后续字幕 / 倍速偏好也放这里。
    - 关闭（默认）：只有「继续观看」入口和播放页的「继续播放」按钮带 `startTime`；
      推荐 / 找片看 / 搜索的普通卡片一律从头播，避免用户想重看却被跳到中间。
    - 开启：普通卡片进入时如果该片有历史，也带上 `startTime`；没有历史仍从头播。
  - 改动在下一次打开视频时生效，不用重启应用。
- **验收**：
  - 默认配置下，普通卡片从头播；继续观看入口落在正确秒数（偏差 < 2 秒）。
  - 开启「自动续播」后，普通卡片也续播；关闭后立即恢复从头播。
  - 从头播放后进度被重置为 0，继续观看卡片同步刷新。
  - 续播与「优先缓存」切换共存时不回到 0（`switchSource` 已保留 `currentTime`）。
- **风险**：`switchUrl` 与 seek 时序冲突；把 seek 放到 `canplay` 兜底一次。

#### A-04 首页「继续观看」轨道

> P0 · 1.5 人日 · v1.2 · 依赖：A-01、A-03

- **目标**：打开应用第一眼就能接着看。
- **做法**：
  - 新增渲染层组件 `src/renderer/src/components/ContinueWatching.tsx`，调 `watch:recent({ limit: 20 })`，
    放在海报叠层和「最新收录」之间；不写进 `home.json`，避免污染推荐配置、备份和 60 秒 feed 缓存。
  - 卡片：封面 + 片名 +「第 12 集 · 剩 34 分钟」+ 底部进度条；`finished` 的最后一部不显示。
  - 单条悬停出现「移除」，走 `watch:clear({ videoKey })`；空数据时整块不渲染。
  - 复用 `VideoCard` 的样式变量，不复制一套新的卡片皮肤。
- **验收**：
  - 空库 / 全部看完 / 缓存不可用时整块消失，不占位、不报错。
  - 有 20 条以上时横向滚动，不出现「共 N 部」类统计。
  - 点击卡片带 `startTime / sourceId / lineIndex / episodeIndex` 打开播放窗。
  - 「继续观看」入口不受 `autoResume` 开关影响，始终续播。
- **风险**：首页已有一段 `home-rail` 的拖动 / 循环逻辑，别硬套；继续观看条用简单横向滚动即可。

#### A-05 剧集面板进度标记

> P1 · 1 人日 · v1.3 · 依赖：A-01

- **目标**：看过的集一眼能认出来，不用猜。
- **做法**：

#### A-06 收藏

> P0 · 2 人日 · v1.3 · 依赖：A-01

- **目标**：把「想看的 / 在追的」留住，成为首页之外的第二个入口。
- **做法**：
  - 业务库新表 `favorites(video_key PRIMARY KEY, video_id, name, created_at)`；`name` 存快照，
    缓存被清后仍能显示「已失效」占位。

#### E-03 IPC 类型单一来源 + 校验

> P1 · 4 人日 · v1.5 · 依赖：E-01

- **目标**：消除 `api.d.ts`（1600 行手写）、`preload/index.ts`、主进程 handler 三处漂移。

  - 新建 `src/shared/ipc.ts`：`interface IpcMap { 'videos:list': { input: [VideoListQuery]; output: VideoListResult } ... }`，

#### E-08 详情缓存上限 + LRU

> P1 · 2.5 人日 · v1.5 · 依赖：无

- **目标**：详情缓存不再无限增长。
- **做法**：
  - 设置 › 存储新增「详情缓存自动清理」分区，三项配置：
    - 开关 `detailCacheEnabled`：**默认开启**；关闭后不再自动淘汰，只保留手动清理。
    - 占用上限 `detailCacheMaxBytes`：**默认 5GB**，可填 GB 数（1–100），0 表示不按体积限制。
    - 保留天数 `detailCacheMaxAgeDays`：**默认 180 天**，可填 0 表示不按时间限制。
  - 启动 5 分钟后与每天一次跑清理：先按天数删过期，再按 `detail_accessed_at` 升序删到低于上限；
    删除文件并重置 `detail_*` 索引，删除走 rename 到 trash 再后台删，避免阻塞。
  - 正在播放 / 正在读取的来源先跳过（读取会刷新 `detail_accessed_at`）。
  - 容量页显示「开关 / 上限 / 当前 / 上次清理释放」；改设置后立即重算一次（不必等下一个周期）。
- **验收**：
  - 默认开启、5GB / 180 天；超限后自动降到上限以下。
  - 关闭开关后不再自动删；改上限 / 天数后立即生效。
  - 播放中的详情不被删；容量页数字与实际目录一致。
- **风险**：清理与采集写详情并发，需要按来源加锁或先标记后删；5GB 在机械硬盘上清理耗时较长，要分页 + 让出事件循环。
