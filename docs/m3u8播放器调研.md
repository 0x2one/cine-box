# 映盒剧场 · m3u8 播放器调研

> 调研时间：2026-11-20。目标：判断本项目要「播 m3u8」需要补什么、选什么、改哪里。
> 结论按「取流架构 → 播放内核 → 改动清单」三层给，最后是待你确认的 6 个问题。

## 一、结论先行

1. 项目里**一个播放器都没有**：无播放器依赖、无 `<video>`、无 HLS / MSE 代码，展示端按 AGENTS.md 的约定是「只展示、不做播放 / 详情页」。
2. 但**输入数据已经齐了**：详情缓存里就有 `playLines[].episodes[].url`，采集侧已按 `.m3u8` 判定可播线路，缺的只是「播放」这一层。
3. **视觉稿也已经有**：`docs/播放页原型.html`（经典 / 专注 / 沉浸三种布局），是海报占位的交互演示，不加载真实视频。
4. 真正的工程难点不在「选哪个播放器库」，而在**取流**：CSP 现在拦死了远程请求、Chromium 桌面端不支持原生 HLS、CDN 普遍校验 Referer/UA 且不给 CORS 头。
5. 推荐组合：**主进程自定义协议代理（`cine-stream://`）+ hls.js + 按原型自绘控制条**。

### 数据侧的两个坑

- **线路名不等于格式**：`flag` 可能是 `m3u8`，也可能是 `jlplayer` / `jlplayer` 这类「网页解析」线路，后者不是视频文件，播放器拿它没办法。UI 上要能把这类线路标成「暂不支持」，而不是点了没反应。
- **m3u8 地址普遍带时效签名**：站点返回的 m3u8 常带 `?sign=…&expire=…` 之类参数，缓存几天的详情里那条 URL 很可能已经 403。播放前应当优先用「重新取一次详情」（`videos:refreshDetail`）的方式拿新鲜地址，并把「线路失效？重新获取」做成兜底动作，而不是只用缓存里那条。

## 三、四个真卡点

### 3.1 CSP 现在会直接拦掉远程视频

`index.html` 的 CSP 是 `default-src 'self'`，只额外放行了 `img-src`。也就是说渲染层：

- 用 `<video src="https://…">` → 被 `media-src`（回落到 `default-src`）拦；
- 用 hls.js 发 XHR/fetch 取 m3u8 与分片 → 被 `connect-src` 拦。

所以不论走哪条路，CSP 都必须动，这是第一个确定要改的地方。

### 3.2 Chromium 桌面端不支持原生 HLS

Electron 44 的 `<video>` 无法直接播 `.m3u8`（只有 Safari / iOS 原生支持）。必须走 MSE，也就是 hls.js 这类**渲染层**库，或主进程转封装（成本高得多，不推荐）。

### 3.3 CORS + 防盗链

采集站的 CDN 通常：不带 `Access-Control-Allow-Origin`、校验 `Referer`、校验 `User-Agent`、部分还校验 `Origin`。

- 浏览器**禁止** JS 改 `Referer`（hls.js 的 `xhrSetup` 也改不了），所以渲染层直连基本没戏；
- 请求必须从主进程发出，主进程可以自由设置 `Referer` / `User-Agent` / `Origin`，同时天然没有 CORS 限制。

### 3.4 m3u8 不能只转发，必须重写

`protocol.handle` 拿到的是「原始 URL → 响应体」，但 playlist 内部是相对路径或跨域绝对路径：

| 需要重写的标签 | 说明 |
| --- | --- |
| 分片行（TS / m4s） | 相对路径要按 playlist 自身 URL 解析成绝对地址 |
| `#EXT-X-KEY:URI="…"` | AES-128 密钥地址，跨域且可能也要带 Referer |
| `#EXT-X-MAP:URI="…"` | fMP4 的 init 分片，漏了就花屏/黑屏 |
| `#EXT-X-MEDIA:URI="…"` | 多音轨 / 字幕轨 |
| `#EXT-X-I-FRAME-STREAM-INF:URI="…"` | 快进预加载用的 I 帧流 |
| `#EXT-X-STREAM-INF` 下一行 | master playlist 的码率子列表 |

另外还要处理：`Range` 请求透传（206 + `Content-Range`）、302 跳转、密钥响应的二进制（不能当文本读）、超时与重试。这一块是主要工作量。

## 四、取流架构三选一

| 方案 | 做法 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- | --- |
| **A. 自定义协议代理** | 主进程 `net.fetch` + `cine-stream://` 协议，重写 playlist、注入 Referer/UA、透传 Range | 与 `cine-img` 同一套路；无端口、无 CORS、能绕防盗链；CSP 只需放行一个 scheme | 要写 playlist 重写器（约 300 行）；CSP 需加 `connect-src` / `media-src` | **推荐** |
| B. 本地 HTTP 代理 | 主进程起 `127.0.0.1:随机端口` | 调试直观，hls.js 无感 | 端口生命周期管理、CSP 要放行 localhost、仍有被扫端口风险 | 备选 |
| C. 渲染层直连 | 放宽 CSP，注入 CORS 头或关 `webSecurity` | 改动最小 | Referer 改不了 → 防盗链站播不了；`webSecurity: false` 是全局安全降级 | 不推荐 |

### A 方案的形状（示意）

```
cine-stream://media/hls?u=<encodeURIComponent(原始URL)>
        │
        ├─ 后缀 .m3u8  → 取文本 → rewritePlaylist(按 base URL 解析) → 返回改写后的文本
        └─ 其它（ts/m4s/key/mp4）
                        → 二进制透传，带 Range / Referer / UA，原样返回状态码与 Content-Range
```

需要注册的协议权限（参考现有 `cine-img`）：`standard`、`secure`、`supportFetchAPI`、`stream`、`corsEnabled`。

3. 体积可通过动态 `import()` 只在进播放页时加载，不影响首屏。

## 八、边界与风险

- **不做 DRM**：Widevine / FairPlay 加密流不做，遇到直接提示不支持。
- **HEVC / H.265 不确定**：Chromium 走系统硬解，部分机器只有声音没有画面，需要在错误态里给出提示。
- **网页解析线路不做**：`jlplayer` 这类要么内嵌 `webview`（等于把第三方网页放进主进程，安全和体验都差），要么丢给外部浏览器，建议明确排除。
- **直播 m3u8**：滑窗不能拖进度，需要单独判断 `EXT-X-ENDLIST`，建议第一版不做。
- **广告切片**：部分站点的 m3u8 里插了广告分片，无法可靠跳过。
- **失效地址**：见「数据侧的两个坑」，播放前应刷新详情。

## 十、自定义图标与加载态

### 10.1 为什么必须关掉原生 controls

浏览器原生 `<video controls>` 的控制条在 Shadow DOM 里，图标、间距、悬停行为都无法用 CSS 覆盖（`::-webkit-media-controls-play-button` 只能隐藏，不能换成自己的 SVG）。所以「自定义播放图标 / 加载图标」只有两种实现：

1. `<video controls={false}>` + 完全自绘控制条 → 图标是你自己的 React 组件，想怎么变态都行；
2. 用带图标插槽的库 → 能换，但受它的 DOM 结构与布局约束。

### 10.2 三条路线的图标可定制程度

| 路线 | 播放 / 暂停图标 | 加载（loading）图标 | 中央大按钮 | 布局自由度 |
| --- | --- | --- | --- | --- |
| **hls.js + `controls={false}` + 自绘**（推荐） | 任意 SVG / 组件 | 任意，可做环形进度、Logo 呼吸、骨架 | 任意 | 完全自由，直接照 `docs/播放页原型.html` |
| ArtPlayer | `icons` 选项支持替换内置图标（`loading` / `state` / `indicator` 等，可传 HTML 字符串或 HTMLElement，见其 `types/icons.d.ts`） | 同上，`loading` 键就是加载图标 | 可换 | 控制条是它的 DOM，深度定制仍要覆盖样式 |
| Vidstack | slot 替换 | slot 替换 | 可换 | 布局可组合，但仍是它的组件树 |
| video.js | 只能 CSS 换 `background-image` | 只能 CSS 改 `.vjs-loading-spinner` | CSS 换 | 皮肤需整体重写 |
| Plyr | `iconUrl` 换整张 sprite，全有或全无 | 同左 | 可换 | 皮肤层，控制条结构不可改 |
| xgplayer | `icons` 配置传 SVG | 同左 | 可换 | 自带 UI 为主 |

结论：需求是「图标要自定义」，并且原型控制条本来就是自绘的，所以**没必要为了图标去迁就某个库的 DOM**。

### 10.3 加载图标不能只监听 `waiting`

只挂 `video.addEventListener('waiting')` 是最常见的坑：它覆盖不到「点了播放 → 首帧出来」这段最长、最需要反馈的时间（少则 1 秒，多则十几秒）。完整状态机应当这样接：

| 阶段 | 触发 | 图标表现 |
| --- | --- | --- |
| 准备 | 点击播放 / 切集 | 中央大播放图标淡出，加载图标淡入 |
| 拉清单 | hls.js `MANIFEST_LOADING` → `MANIFEST_PARSED` | 加载图标（可带「正在连接线路」文案） |
| 拉首片 | hls.js `FRAG_LOADING` → `FRAG_LOADED` → `BUFFER_APPENDING` → `FRAG_BUFFERED` | 加载图标；此时可用 `FRAG_LOADING` 的 `frag` 序号做不确定进度环 |
| 出首帧 | video `loadedmetadata` / `canplay` / `playing` | 加载图标淡出，控制条淡入 |
| 播放中缓冲 | video `waiting` / `stalled` | 中央小号加载图标出现，不清空控制条 |
| 恢复 | video `playing` / `canplay` | 加载图标消失 |
| 卡死判定 | `waiting` 持续 > 3s 且 `hls` 无新分片 | 升级为「网络慢」提示 + 手动重试 |
| 失败 | hls.js `ERROR`（`NETWORK_ERROR` / `MEDIA_ERROR` / `OTHER_ERROR`）+ video `error` | 错误图标 + 原因文案 + 「重试 / 换线路」 |
| 结束 | video `ended` | 中央播放图标复现（或自动下一集倒计时） |

关键点：**hls.js 的 `ERROR` 事件里带 `fatal` 标记**，只有 `fatal === true` 才该真的进错误态；非 fatal 的（比如某个分片 404）hls.js 自己会重试或跳过，UI 不应闪错误。

### 10.4 组件 API 草案

```tsx
// src/renderer/src/components/HlsPlayer.tsx
export interface PlayerIcons {
  play?: React.ReactNode // 中央大播放
  pause?: React.ReactNode // 控制条暂停
  loading?: React.ReactNode // 加载中（首帧 + 缓冲共用，可再拆）
  buffering?: React.ReactNode // 播放中缓冲（可选，不传就复用 loading）
  error?: React.ReactNode
  retry?: React.ReactNode
  volume?: React.ReactNode
  muted?: React.ReactNode
  fullscreen?: React.ReactNode
  exitFullscreen?: React.ReactNode
  next?: React.ReactNode
  list?: React.ReactNode
  rate?: React.ReactNode
}

export interface HlsPlayerProps {
  src: string
  poster?: string
  /** 不传则用内置的一套（与原型一致的线性图标） */
  icons?: PlayerIcons
  autoPlay?: boolean
  startTime?: number // 续播
  onTimeUpdate?: (time: number, duration: number) => void
  onEnded?: () => void
  onError?: (error: PlayerError) => void
  /** 加载文案（默认「正在连接线路」） */
  loadingText?: string
}
```

图标一律走 `ReactNode`，默认实现用内联 `<svg>` + `currentColor`，这样：

- 深色 / 浅色主题自动跟着 `--text` / `--accent` 走，不用两套图标；
- 不额外请求图片，不碰 CSP；
- 与项目现有 `.ic` 图标的写法一致（原型里就是 `<svg><use href="#i-play"/></svg>`）。

### 10.5 还可以再进一步的两个点

- **加载图标带进度**：hls.js 不给「总字节数」，但 `FRAG_LOADING` 的 `frag` 与 `level.details.fragments` 能算出「第几片 / 共几片」，做成确定进度环比纯转圈更有反馈。
- **首帧遮罩**：用海报图 + 模糊作为加载背景，避免黑屏；首帧出来后再移除，视觉上和原型一致。

### 11.2 逐个说

**MuiPlayer —— 直接出局：GPL-3.0。**
`mui-player` 的 `license` 字段是 GPL-3.0。本项目是要分发安装包的桌面应用，GPL-3.0 的传染性会要求整个应用以 GPL 发布，和当前 MIT 不兼容（除非产品整体转 GPL）。另外它 npm 停更在 2023-01、无 TS 类型、月下载 937，内置图标也没有替换 API（只能在 `custom.headControls` / `footerControls` / `rightSidebar` 里加自己的按钮，每处最多 5 个）。

**DPlayer —— 能用但等于自己写。**
它是弹幕播放器，m3u8 要 `video.type: 'customHls'` 并自己把 hls.js 实例塞进去；图标没有任何 API，只有 `theme` 换主色。npm 最后一次发布是 2023-07（仓库 2026-11 还有零星提交），React 封装 `react-dplayer` 停在 2022。下载量不小（2.5 万/月）主要是存量项目。它的「清晰度」是换 URL，不是切 hls.js 的 level，做不了「1080P / 高码率」这种真·码率切换。

**ZWPlayer —— 最不合适的一个。**
- **核心不开源**：GitHub 上那个仓库只放构建产物（README 自述），npm 包里是 `public/zwplayer` 的 minified bundle，源码不可审计、出问题改不了。
- **接法别扭**：`postinstall` 把核心拷进 `public/zwplayer`，运行时**动态加载脚本**。本项目 CSP 是 `script-src 'self'`（没有 `'unsafe-inline'`），它若注入内联脚本会直接被拦；打包时还要保证 `out/renderer/zwplayer` 被带上。
- **图标换不了**：参数表里只有 `logo`（台标图片，可定位/透明度）、`watermarks`、`disablePlayBtn` / `disableSeek` 这类开关，没有替换播放 / 加载图标的入口。它的定制方式是官网「代码生成器」生成一套皮肤配置，不是给你图标插槽。
- **依赖奇怪**：peer 里要求 `react-router-dom`，一个播放器不该绑路由。
- 好处确实有：全协议、字幕、章节、弹幕、水印，月下载 139。

**ArtPlayer —— 四者里唯一可考虑。**
MIT、有 TS 类型、活跃（2026-03 发布、2026-10 提交）、12.4 万月下载、4.2k star。`icons` 是全量可换的，另有 `layers`（自定义浮层，可以放自己的大播放按钮）、`controls`（自定义按钮）、`setting` 面板、`playbackRate`、`aspectRatio`、`fullscreenWeb`、`pip`、`screenshot`、`miniProgressBar`、`theme`。m3u8 通过 `customType` 接 hls.js，能拿到实例做码率切换。

但要注意：**它的控制条结构仍是它自己的**。原型里的「胶囊集数」「三种布局」「侧栏选集」都要重新搭，等于在它的 DOM 上再糊一层，最后大概率变成「用 ArtPlayer 的 video 内核 + 把它的控制条全隐藏，再自己画一遍」——那不如直接用 hls.js。

### 11.3 对本项目的结论

1. 四个库**都解决不了取流问题**：它们全在渲染层发请求，CSP、CORS、Referer 三关照样要过。主进程 `cine-stream://` 代理仍然是前提，跟选哪个库无关。
2. 四个库里，**三个换不了内置图标**；唯一能换的 ArtPlayer，其 UI 结构和原型冲突。
3. 所以选型不变：**hls.js（内核）+ 自绘控制条**。如果一定要用现成插件，只有 ArtPlayer 值得试，且要接受「先隐藏它的控制条、再叠自己的 UI」，工作量并不比自绘少。
4. MuiPlayer 因 GPL-3.0 建议永久排除；ZWPlayer 因闭源核心 + 无图标 API 排除；DPlayer 若无历史包袱也不必考虑。
