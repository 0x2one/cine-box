# 映盒剧场 · 投屏功能可行性调研

> 调研时间：2026-11-28。对应待办 `D-04 投屏（DLNA / Cast）`、决策项 `D8`。
> 目标：判断播放页能不能加「投屏」，走哪条协议，代价多大，先验证什么。
>
> **2026-11-28 更新：v1 已按本方案落地并通过两台真机验证，实施记录见第十二节；下面的调研判断保留，方便对照。**

## 一、结论先行

1. **发现和控制这一层可行，已经跑通。** 纯 Node（`dgram` + `http`）实现 SSDP 发现、设备描述解析、`ConnectionManager.GetProtocolInfo`、`AVTransport.SetAVTransportURI / Play / Pause / Stop`，假电视自测通过；真机也完成了投屏与停止（暂停 / 继续待补）。
2. **缓存集真机试投已完成：两台设备都能播。** 用本机 HTTP 服务把下载好的缓存包（`大王饶命3 第14集`，365 个 TS 分片、24:19、无加密）暴露到局域网后，两台设备都进入了 `PLAYING` 并按分片顺序播放：
   - **JMGO N3（当贝 MediaRenderer）**：能播；但原始缓存播放列表里的 `#EXT-X-DISCONTINUITY` 会让它跳段（1-8 → 24-28 → 81-86 → 134-139），去掉这些标签后按 1、2、3… 顺序正常播。
   - **Bilibili 小电视（K970）**：能播，且原始列表就按顺序播；它的 SinkProtocolInfo 里**根本没有声明 HLS**，说明能力表只能当参考，不能作为「能不能投」的唯一依据。
3. **本项目已经有投屏需要的全部底层设施**：`lan/lan-proxy.ts` 会改写 m3u8、补 Referer/UA、代理分片和密钥；`lan/lan-cache.ts` 能把缓存包按 Range 发给别人；`ffmpeg-static` 已经在依赖里；`lan-config.ts` 已经会挑局域网地址。投屏主要是「发现 + SOAP + 一个只服务投屏的临时 HTTP 服务」这三块新代码。
4. **建议分三期**：
   - v1（约 7 人日，见第九节）：DLNA 发现 + 设备选择 + HLS 直推（在线集 + 缓存集）+ 暂停/继续/停止 + 播放页 UI；
   - v1.1（约 1.5 人日）：设备不认 HLS 时用 ffmpeg 实时转封装 MPEG-TS 兜底（不支持 seek）；
   - v2（可选）：Chromecast（`castv2-client`）；AirPlay 不做，Electron/Chromium 没有可用的发送端 API。
5. **不建议把「所有电视都能投」当验收标准。** 真机已经证明两台设备的实现差异很大（是否声明 HLS、怎么处理 discontinuity、要不要 Range 都不同），投屏只能做到「尽量兼容 + 失败时说清楚原因」。真正可承诺的是：同一局域网能发现设备、能播放本机 HLS 缓存、暂停/继续/停止可控；在线集通过本机代理转成局域网 HTTP 后再投（远程 HTTPS 直投在当贝上实测失败，见 2.3）。

## 二、本次实测记录

环境：Windows（WLAN，网络配置文件为「公用」），Node 26.13，项目 Electron 44。

### 2.1 真机发现

用 `tmp/cast-spike.mjs` 发送 `M-SEARCH`（`ST: urn:schemas-upnp-org:device:MediaRenderer:1` 与 `AVTransport:1`，每轮 3 次），每块网卡各一个 socket：

| 设备 | 厂商 | SinkProtocolInfo 条数 | 声明支持 HLS | 关键格式 |
| --- | --- | --- | --- | --- |
| 我的小电视（K970） | Bilibili Inc. | 32（音视频 28） | 否 | WMV / ASF / MPEG-PS / LPCM / MP3 |
| JMGO-N3-0820 | 当贝 | 138（音视频 131） | 是（`video/m3u8`） | MP4 / MP2T / MPEG / MKV / HLS |

> `SinkProtocolInfo` 只是设备「声明」的能力，不能当判定依据：实测 Bilibili 没声明 HLS，照样把 HLS 播了（见 2.3）。它的用途是**选 content type 和决定兜底顺序**，不是直接判死。

两台设备都能正常返回 `GetTransportInfo`（均为 `NO_MEDIA_PRESENT`）、`GetMediaInfo`、`GetVolume`，SOAP 控制地址可用。

> 以上是只读探测（`GetProtocolInfo` / `GetTransportInfo` / `GetVolume`）；真机试投见 2.3。

一个**必须记住的坑**：第一版探针把 socket 绑在 `0.0.0.0` 再用 `setMulticastInterface()` 指定网卡，结果一台设备都发现不了；改成**每块网卡各绑一个 socket、用该网卡的地址发送**之后，立刻发现两台。Windows 多网卡（本机还有一块手机热点虚拟网卡 `192.168.137.1`）下，这条差异是决定性的。

### 2.2 假电视自测（协议链路）

`node tmp/cast-spike.mjs --mock`：

```
SSDP 发现 → 设备描述 → GetProtocolInfo（判断 HLS）
→ SetAVTransportURI（带 DIDL-Lite + protocolInfo）
→ Play → GetTransportInfo(PLAYING) → Pause → PAUSED_PLAYBACK
→ Play → PLAYING → Stop → STOPPED
MOCK 验证通过 ✅
```

说明「发现 → 控制 → 状态回读」这条链路本身没有协议障碍，剩下的都是工程问题。

### 2.3 真机试投（缓存集）

用 `tmp/serve-hls.mjs` 在 `0.0.0.0:8123` 上把本机缓存包（`大王饶命3 第14集`，365 个 TS、无加密、总长 24:19）当静态站点发出来，再分别投给两台设备；服务端记录每一笔请求，用来判断电视到底有没有来拉流。

| 设备 | 原始播放列表（带 `#EXT-X-DISCONTINUITY`） | 去掉 discontinuity 的播放列表 |
| --- | --- | --- |
| JMGO N3（当贝） | `PLAYING`、时长 24:19，但 12 秒内分片请求是 1-8 → 24-28 → 81-86 → 134-139，`RelTime` 一路跳到 9:00 | 顺序请求 1-7，`RelTime` 0→11s，正常 |
| Bilibili 小电视 | `PLAYING`、时长 24:19，顺序请求 1-5，`RelTime` 0→8s | 未重复测（原始已正常） |

补充现象：

- **两台设备都真的来拉流了**，不是只回了一个 `PLAYING` 状态；请求来自 `192.168.68.183`（两台设备恰好同一个 IP，可能是同一台投影上的两套 DMR 服务）。
- **当贝对播放列表和分片都发 `Range: bytes=0-`**，服务端必须回 206；Bilibili 用普通 200。投屏服务两种都要支持。
- **Bilibili 的 SinkProtocolInfo 没有 HLS，却把 HLS 播了**；说明能力表只能用来选 content type / 兜底顺序，不能用来直接判死。
- **当贝第一次 `Stop` 后仍报 `PLAYING`**，过几秒再查才是 `STOPPED`；停投后要允许一小段状态收敛时间。
- **把远程 HTTPS 的 Apple HLS 直接投给当贝**：`SetAVTransportURI` + `Play` 都返回成功，但状态一直 `STOPPED`，本机服务也没有收到任何请求——设备根本没去拉。生产架构里本来就要把在线流经本机 HTTP 代理再投（见 5.1），这条不构成阻碍，但**不能把第三方 HTTPS 地址直接交给电视**。
- **SSDP 会丢包**：第一次投完后再发现，出现过一次 0 台，隔两秒重发又恢复。正式实现要发 3 轮（间隔 600ms）并允许手动刷新。

### 2.4 网络与防火墙

- Windows Defender 防火墙三个配置文件都是开启状态；`node.exe` 与 `electron.exe` 已有入站规则，所以本机探测正常。
- 打包后的应用第一次监听端口时，Windows 仍可能弹「是否允许访问网络」；用户点取消，电视就取不到流。这一点要在 UI 里给出可操作的错误提示。
- 当前 WLAN 被识别为「公用」网络。公用配置文件下入站默认更严，且访客 Wi-Fi / AP 隔离会让发现直接为 0。发现失败时的文案要覆盖这两种情况，不能只说「没有设备」。

## 三、现状盘点：能复用什么

| 资产 | 位置 | 对投屏的价值 |
| --- | --- | --- |
| HLS 代理 + 播放列表改写 | `src/main/lan/lan-proxy.ts` | 直接复用：电视拿到的是改写后的 m3u8，分片 / 密钥 / init 都走本机，防盗链由主进程补 Referer/UA 解决 |
| 缓存包 Range 下发 | `src/main/lan/lan-cache.ts` + `lan-service.ts` 的 `sendCacheFile` | 缓存集投屏直接复用（需把 `sendCacheFile` 提取成共享函数） |
| 局域网地址枚举 | `src/main/lan/lan-config.ts` | 选和电视同网段的那个 IP |
| 统一代理配置 | `network-manager.ts` + `net.fetch` | 投屏的上游请求和采集 / 局域网共享共用 off / system / custom，切系统代理不用改投屏代码 |
| ffmpeg | `ffmpeg-static` + `src/main/mp4-export.ts` | 兜底转封装 MPEG-TS 时直接用，进程管理 / `asarUnpack` / 签名都已配好 |
| 播放器控制条扩展 | `src/renderer/src/player/useArtPlayer.ts` | 「选集」「缓存」已经有插图标按钮的成熟写法，加一颗「投屏」照抄即可 |
| 播放入口 / 详情 | `player:open`、`videos:detail`、`detailCache` | 主进程能独立校验「这个 videoId 有没有这条 URL」，不需要信任渲染层 |

**缺口**：

1. 播放地址只存在于渲染层；主进程需要按 `videoId` 重新校验 URL 归属。
2. 缓存播放用的是 `127.0.0.1:<随机端口>`（`download-hls-server.ts`），电视访问自己的 loopback，必然失败；投屏必须换成**局域网地址**。
3. 局域网影院服务是「整套网页 + 片库接口」，默认不开，也不该为了投屏悄悄把整个片库暴露出去；投屏应另起一个只服务当前会话的临时服务。

## 四、协议选型

| 协议 | 本次环境 | 可行性 | 结论 |
| --- | --- | --- | --- |
| **DLNA / UPnP AV** | 发现 2 台 | 高。SSDP + SOAP 都是纯文本 HTTP，无原生依赖 | **v1 主方案** |
| Chromecast | 未发现 | 中。`castv2-client` 可用，默认接收器支持 HLS；国内设备少 | v2 可选 |
| AirPlay | 未发现 | 低。Electron/Chromium 没有 AirPlay 发送端 API，纯 JS 无法把视频 URL 交给 Apple TV | **不做** |
| Miracast / 系统投屏 | — | 系统级能力，不能按窗口 / 按片源触发 | 不做 |
| 商业投屏 SDK（乐播等） | — | 需要商务授权与原生集成，和 MIT 分发冲突 | 不做 |

DLNA 侧需要的服务和动作（够用即可，不用实现完整 UPnP）：

- 发现：`M-SEARCH` → `LOCATION` → 设备描述 XML → `serviceList` 里取 `AVTransport`、`RenderingControl`、`ConnectionManager` 的 `controlURL`；
- 能力：`ConnectionManager.GetProtocolInfo` 的 `Sink`；
- 控制：`AVTransport.SetAVTransportURI`（带 DIDL-Lite 元数据）、`Play`、`Pause`、`Stop`、`GetTransportInfo`、`GetPositionInfo`；
- 音量（可选）：`RenderingControl.GetVolume / SetVolume`；
- 事件订阅（GENA）v1 不做，用 2 秒轮询 `GetTransportInfo` 代替。

## 五、推荐架构

```
播放页（React，独立播放窗）
  控制条「投屏」图标 → window.api.cast.devices() / start() / stop()
        │  IPC
主进程 src/main/cast/
  cast-service.ts    会话状态机：发现→连接→播放→暂停→停止；轮询；事件广播
  cast-discover.ts   SSDP（每网卡一个 socket）+ 描述解析 + 能力探测（缓存 5 分钟）
  cast-control.ts    SOAP 客户端（AVTransport / RenderingControl）
  cast-server.ts     局域网 HTTP（随机端口，只服务当前会话）
  cast-remux.ts      ffmpeg 实时转封装（v1.1）
```

### 5.1 投屏媒体地址

投屏会话开始时，`cast-server` 起在 `0.0.0.0:0`，选一个和电视同网段的地址，生成：

```
在线集：http://<lan-ip>:<port>/cast/<token>/index.m3u8
缓存集：http://<lan-ip>:<port>/cast/cache/<recordId>/index.m3u8
兜底：  http://<lan-ip>:<port>/cast/<token>/index.ts
```

- `<token>` 是每次会话随机生成的 32 位十六进制，映射到 `{ url, title, videoId, recordId }`；投屏入口只认映射表，不接受外部传任意 `?u=`（播放列表改写出来的 `/api/play.m3u8?u=…` 仍受代理的来源白名单约束）。**原始播放地址只留在主进程，不写进 DIDL，也不交给电视。**
- 播放列表里的相对地址会被 `createMediaProxy` 改写成同服务的 `/api/play.m3u8?u=…` 与 `/api/stream?u=…`；这两个路由只在 `allowedOrigins` 登记过的域上工作（和局域网影院同一套白名单）。
- 缓存集走 `lanCache.resolveFile` + Range 下发，支持拖动。
- 会话结束 / 播放窗关闭 / 应用退出时关服务、杀 ffmpeg、清 token。

#### 为什么在线集也必须走本机代理

在线集不把第三方地址直接交给电视，和局域网影院的做法保持一致：**电视只访问本机 HTTP，主进程用 `net.fetch` 去取上游**。这样做的收益：

1. **代理设置只有一处**：`net.fetch` 走 `session.defaultSession`，而 `network-manager.ts` 已经把「设置 › 网络」的 off / system / custom 套在这个 session 上；投屏、采集、在线检索、局域网共享因此共用同一份代理配置和 bypass 规则（本机 / 内网 / `.local` 不走代理）。用户切「使用系统代理」时，投屏自动跟着变，不需要再为投屏单独实现一套。
2. **防盗链 / UA / HTTPS 一次解决**：上游该补的 Referer / UA、HTTPS 证书、302 跳转都由主进程处理；电视只需要支持普通 HTTP HLS。实测把远程 HTTPS 的 Apple HLS 直接投给当贝，`SetURI` 成功但设备根本没去拉；本机 HTTP 的缓存包则能正常播放，证明这条差异是真实的。
3. **地址不泄露、可撤销**：电视看到的是带 token 的本机地址，原始签名地址和密钥只在主进程；停投即失效。
4. **可以统一做兜底**：设备不认 HLS 时，ffmpeg 也是从本机代理地址取流再转封装，代理配置、超时、重试只有一套。
5. **可观测**：所有上游请求都经过主进程，日志、失败原因、限速 / 并发控制都容易加。

代价也要说清楚：投屏期间桌面端必须保持运行且能联网（应用退出 = 电视断流）；用户中途切换代理会让 `network-manager` 调 `closeAllConnections()`，在途分片可能 502，需要电视重试或投屏服务自动重连；电视必须能访问到本机的局域网地址（防火墙 / AP 隔离）。这些都比「把原始地址交出去」更可控，建议作为硬约束写进实现：**投屏入口只接受本机地址，不实现「直投原始链接」分支**。

### 5.2 主进程校验

渲染层只传「我现在播的是哪一集」：

```ts
{ kind: 'remote', videoId, url }   // 主进程用 detailCache 校验 url 确实属于该 videoId，且未被 18+ 隐藏
{ kind: 'cache', recordId }        // 主进程用 downloadStore 校验记录可播
```

不把 `fileUrl` / 任意 URL 直接交给投屏服务，避免把 `player:open` 的白名单约束绕过去。

### 5.3 播放页交互

- 控制条右侧新增「投屏」图标（22×22 SVG，和「缓存」「选集」同一套 `.art-icon` 样式，`index` 排在 24 / 25 之后）。
- 点击弹出设备列表（复用 `.episode-popover` 的浮层样式）：设备名 + 型号、刷新、失败提示；记住上次设备（`localStorage`）。
- 投屏中：本地视频暂停，播放区盖一张「正在投屏到 XXX」的状态卡，提供「暂停 / 继续 / 停止」；停止时按电视的 `GetPositionInfo` 回到本机对应位置继续播。
- **全屏时浮层看不见**（浮层在 ArtPlayer 元素外面）：点投屏时先 `document.exitFullscreen()`，和「选集」按钮的处理一致。
- 换集 / 自动连播：v1 重新 `SetAVTransportURI` 到新一集（新 token）；设备不支持就停投并提示。
- 错误态：未发现设备、连接失败、设备拒绝 URL、播放 8 秒未进入 `PLAYING`、电视中途停止，各给不同文案。

## 六、格式兼容策略

### 6.1 先试 HLS，再按设备兜底

```
投屏时先用本机代理地址试 HLS（不管 Sink 有没有声明——Bilibili 没声明也照样能播）
  ├─ 8 秒内进入 PLAYING / 进度在走 → 用 HLS（可拖动，体验最好）
  └─ 没进 PLAYING / SOAP 报错    → 用 ffmpeg 转封装 TS 再试（contentType 从 Sink 里挑）
       └─ 还不行                 → 明确告诉用户「该设备不支持当前片源」，建议换设备或缓存后投
```

**不要用 SinkProtocolInfo 直接判死。** 它只用来做两件事：挑 `protocolInfo` / `Content-Type`（当贝声明的是 `video/m3u8`，不是标准的 `application/vnd.apple.mpegurl`；TS 同理 `video/mp2t` / `video/MP2T` / `video/mpeg`），以及决定失败后先试 TS 还是先试 MPEG-PS。

### 6.2 HLS 直推（本机代理，首选）

- 电视拉的是 `<lan-ip>/cast/<token>/index.m3u8`，主进程再用 `net.fetch` 取上游并改写播放列表；暂停 / 继续 / 拖动都由电视自己处理，体验最好。
- 这里的「直推」指**不转封装**，不是「把原始地址直接给电视」。原始地址一律不写进 DIDL，也不做「直投远程链接」的分支。
- 上游是签名 URL 时，投屏前先走一次 `videos:detail:refresh`（或至少校验），避免投出去就是 403；播放列表里的密钥 / 分片仍由本机代理按需取。

### 6.3 MPEG-TS 兜底（v1.1）

```
ffmpeg -i http://127.0.0.1:<port>/cast/<token>/index.m3u8 \
       -c copy -f mpegts pipe:1
```

- 不重编码，CPU 很低；AES-128 / fMP4 由 ffmpeg 处理。
- 响应 `Content-Type: video/mp2t`、`transferMode.dlna.org: Streaming`、chunked；**没有时长，不能拖进度**，UI 要写明「兼容模式 · 不支持拖动」。
- 小电视 K970 没声明 MP2T，但它连 HLS 都是「没声明却能播」，所以 TS 也值得先试一次；`-f mpeg`（MPEG-PS）只作为老设备的最后兜底，H.264 进 PS 不保证，失败就明确标注「该设备不支持」。
- 源是 HEVC 时，电视不一定能解；可选「转 H.264」但很吃 CPU，不建议放进 v1。

### 6.4 缓存集

- 缓存包是本地 HLS，`/cast/cache/<recordId>/index.m3u8` 直接可播，拖动天然支持；**两台真机都已验证**。
- **Range 必须支持**：当贝对播放列表和分片都发 `Range: bytes=0-`，要回 206；Bilibili 用 200。`sendCacheFile` 已经实现了单段 Range，提取出来复用即可。
- **discontinuity 要处理**：缓存包保留了源站的 `#EXT-X-DISCONTINUITY`，当贝会因此跳段（Bilibili 正常）。实测把播放列表里的 discontinuity 标签去掉后，当贝按顺序播放。建议投缓存集时默认下发「净化后的播放列表」；如果遇到音画不同步 / 卡顿，再升级为 `ffmpeg -c copy -f mpegts` 重封装（时间戳连续，代价是一次几秒到几十秒的转封装）。
- 需要兜底时，先把缓存包转成一个临时 `.ts`，再用 Range 下发，**拖动也能用**——这是缓存集相对于在线集的优势。

## 八、依赖取舍

| 方案 | 评价 |
| --- | --- |
| **自写 SSDP + SOAP，只加 `fast-xml-parser`** | **推荐**。发现逻辑约 150 行，SOAP 约 200 行；能控制「每网卡一个 socket」、超时、错误文案；不受 `node-ssdp` 绑定 1900 端口的影响 |
| `node-ssdp@6` + 自写 SOAP | 可用。v6 是 2026 年仍在维护的版本（Node ≥ 22.12，CommonJS），但 Client 会占用 UDP 1900 收 NOTIFY，和系统 SSDP 服务/其它投屏软件可能打架 |
| `upnp-mediarenderer-client@1.4` | 省事但版本停在 1.4.0，依赖 `elementtree` / `upnp-device-client` 都比较老，错误处理和超时不可控；只适合做 spike |
| `castv2-client@1.2` | Chromecast 唯一现实选择，协议稳定；v2 再引入 |

`fast-xml-parser` 是纯 JS、无原生依赖、有 CJS 入口，打包没有额外负担。如果不想加依赖，设备描述和 SOAP 响应都是很扁的 XML，用正则 + 实体反转义也能覆盖（本次 spike 就是这么做的）；但正式实现建议用解析器，避免某些电视的描述里有 CDATA / 命名空间前缀。

## 十、风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 电视不认 HLS | 老设备直接不可投 | 先试 HLS（不依赖 Sink 声明）+ TS 兜底 + 明确文案；不承诺全设备 |
| 电视只认 MPEG-PS / WMV | 极老设备可能始终失败 | 标记「不支持」，后续用 `-f mpeg` 再试；K970 实测能播 HLS，不要按能力表提前判死 |
| 兼容模式不能拖进度 | 体验差 | UI 标注；缓存集走「先转 TS 再下发」保住拖动 |
| 防火墙 / 公用网络 / AP 隔离 | 发现为 0 或电视取不到流 | 分场景文案；首次投屏引导允许防火墙；提示检查访客网络 |
| 多网卡选错地址 | 电视访问不到 | 按电视 IP 找同网段的本机地址；找不到再退回第一块网卡 |
| macOS 本地网络权限 | 发现 / HTTP 都被系统拦 | Info.plist 加 `NSLocalNetworkUsageDescription`，首次弹窗 |
| 签名 URL 过期 | 投出去 403 | 投屏前刷新详情；失败提示「重新打开这一集」 |
| 投屏中切代理 / 断网 | 在途分片 502、画面卡住 | `network-manager` 切代理时会 `closeAllConnections()`；投屏服务对上游失败做一次重试，界面提示「网络已切换」；电视侧一般会自己重试分片 |
| HEVC / 多音轨 | 有画面没声音 / 黑屏 | 读 `Sink` 与 ffmpeg 探测；不支持时提示换线路 |
| ffmpeg 进程泄漏 | 后台占 CPU | 会话结束 / 窗口关闭 / 退出统一 kill；`before-quit` 兜底 |

### 12.4 已知限制

- **没有 MPEG-TS 兜底**：只支持能播 HLS 的设备；完全不认 HLS 的老设备会停在 `starting` → 报「电视没有开始播放」。
- **master 压平需要预取一次**：用 `net.fetch` + Referer / UA 去取；如果源站对 master 的防盗链比媒体列表更严，预取失败就退回原地址，电视可能仍失败。
- 没有 GENA 事件、音量控制、UI 拖动进度；`cast:seek` 已有 IPC，但界面没放入口。
- 投屏开始会按本地当前进度 seek（起播 600ms 后发 Seek），个别设备可能忽略；不支持 Seek 的设备会从 0 开始。
- 只做 DLNA；Chromecast / AirPlay 未实现。
- 某些电视的 DMR 只在它自己的投屏 App 在前台时广播（Bilibili 小电视实测切到别的投屏后会消失），设备列表里看不到时先在电视上打开对应 App。



临时脚本在 `tmp/cast-spike.mjs` 与 `tmp/serve-hls.mjs`（按项目约定不提交）：

```bash
# 1) 只发现 / 只读检查
node tmp/cast-spike.mjs                          # 发现设备（每网卡 socket，3 轮 M-SEARCH）
node tmp/cast-spike.mjs --protocol --inspect     # 能力 + 当前状态 + 音量（只读）

# 2) 假电视自测

# 3) 真机投缓存包（会真的播放）

node tmp/cast-spike.mjs --cast "http://<本机局域网 IP>:8123/index.m3u8" --name 当贝 --seconds 12 --content-type video/m3u8
node tmp/cast-spike.mjs --cast "http://<本机局域网 IP>:8123/clean.m3u8" --name 当贝   # 去掉 discontinuity 的版本
```

`serve-hls.mjs` 会打印每一笔电视请求（源 IP / Range / 状态码），用来判断设备到底有没有来拉流；`/clean.m3u8` 是去掉 `#EXT-X-DISCONTINUITY` 的虚拟播放列表。

`cast-spike.mjs` 里已经包含：每网卡 SSDP、描述解析、`GetProtocolInfo`、DIDL-Lite、`SetAVTransportURI / Play / Pause / Stop / GetTransportInfo / GetPositionInfo / GetVolume`，以及一个可复用的假电视。正式实现可以直接把它拆成 `cast-discover.ts` / `cast-control.ts`。
