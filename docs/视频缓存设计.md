# 视频缓存设计（SQLite 列表 + 文件详情）

> 状态：已实施（v1.1）
> 日期：2026-11-18
> 范围：采集站的视频列表、视频详情、采集进度的缓存设计；本文同时记录实现落点。
> 关联文档：[采集接口参数说明](./采集接口参数说明.md)

---

## 1. 背景与目标

采集接口（`ac=list` / `ac=detail`）一次能返回分页数据，但站点多、数据量大，播放地址和简介体积也不小。直接每次打开页面都请求站点，速度慢且不可控；全部塞进一个 SQLite 又会让库文件、WAL、备份和启动成本一起变大。

因此采用 **SQLite + 文件缓存** 的分层方案：

- **SQLite**：存列表页需要的结构化数据、搜索索引、多站合并关系、采集进度、站点对账信息，以及**详情缓存索引**。
- **文件缓存**：详情页的完整正文（完整简介、播放线路、导演等）放 JSON 文件，位于 `userData/Data/videos` 下；演员和标签作为来源字段留在 SQLite。
- **SQLite 维护详情索引**：`video_sources` 记录详情文件路径、大小、缓存时间、最近访问时间、源数据快照和错误状态；**不存详情正文**。详情读取先查索引，索引不存在/文件缺失时实时抓取，写文件并回填索引，后续直接走缓存。
- **容量可见**：控制台显示 SQLite 与详情文件缓存的体积，支持分别清理详情缓存和全部缓存。

目标：

1. 列表页打开快，默认按更新时间倒序，支持百万级名字模糊搜索。
2. 多站视频按名字合并成同一个视频资源，但每个站点保留独立来源。
3. 详情页按需缓存，缓存后再次打开不再请求站点。
4. 采集可中断、可续采，进度落库。
5. 缓存再大，启动时不扫描大表、不遍历详情目录、不重建索引。
6. 缓存可独立清理，不影响站点、分类、绑定等业务数据。
7. 控制台提供手动/定时采集入口，按站点查看采集进度，采集运行日志实时可见。
8. 控制台「容量」显示 SQLite 与文件缓存体积，支持手动清理详情缓存/全部缓存。

## 2. 非目标

- 本阶段只做控制台的采集 / 进度 / 日志 UI，不做首页视频列表 / 详情页 UI。
- 不做多计划、复杂 cron 表达式；本版每个站点一条固定间隔计划。
- 不做按容量或时间的 LRU 淘汰（先提供手动清理与统计）。
- 不做模糊资源合并（不解析“国语版”“4K”“第 N 季”等别名）。
- 不把视频缓存放进现有备份；采集计划属于用户配置，需要加入备份（业务表从四张变为五张）。
- 不做远程搜索；搜索只查本地缓存。
- 不在 SQLite 里存详情正文；SQLite 只维护详情索引（路径/大小/时间/状态），正文仍放 `Data/videos` 的 JSON 文件。

## 3. 总体架构

```text
        ┌──────────────────────────────────────────────┐
        │        userData/Data/cine-box.db             │
        │  业务库（已有）                              │
        │  ├─ sites / site_categories / ...            │
        │  └─ collect_schedules   定时采集计划          │
        └──────────────────────────────────────────────┘
                           │ 计划到点入队
                           ▼
        ┌──────────────────────────────────────────────┐
        │        采集调度器 + 单队列                    │
        │  collect-scheduler → video-collector         │
        │  手动 / 定时都进入同一队列                    │
        └──────────────────────────────────────────────┘
                           │ 写列表 / 写日志
                           ▼
        ┌──────────────────────────────────────────────┐
        │        userData/Data/video-cache.db          │
        │  SQLite（只存列表/索引/进度/日志）            │
        │  ├─ videos              合并后的视频          │
        │  ├─ video_sources       来源/列表/详情索引    │
        │  ├─ videos_fts          名字搜索索引          │
        │  ├─ collect_progress    采集进度              │
        │  ├─ collect_logs        采集日志              │
        │  └─ cache_sites         站点对账              │
        └──────────────────────────────────────────────┘

        ┌──────────────────────────────────────────────┐
        │        userData/Data/videos/                 │
        │  <siteId>/<safeSourceVideoId>.json           │
        │  详情页完整数据（简介、播放线路等）           │
        │  路径由 detail_path 索引或推导               │
        └──────────────────────────────────────────────┘
```

数据流：

- 采集列表：手动或定时入队 → 请求站点 → 解析 → 写 `videos` / `video_sources`（列表字段）→ 更新 `collect_progress`、写 `collect_logs`。不写详情文件。
- 定时采集：`collect_schedules` 到点 → 入同一队列；不直接访问站点。
- 详情读取/刷新：先查 SQLite 详情索引；命中读文件，未命中/文件丢失实时抓取 → 写详情 JSON 文件 → 回填索引。
- 列表读取：只查 SQLite，不读文件。
- 搜索：只查 SQLite FTS。
- 进度/日志：控制台读 `collect_progress` / `collect_logs`，并通过事件实时更新。
- 容量：控制台读 `detail_size` 索引聚合 + SQLite 文件 `stat`；需要时扫描详情目录校对。

## 4. 为什么这样拆分

| 数据 | 存放位置 | 原因 |
|---|---|---|
| 视频名称、封面、更新进度、分类、简介摘要、更新时间 | SQLite `videos` / `video_sources` | 列表高频读取，需要排序、过滤、分页、合并 |
| 名字搜索索引 | SQLite FTS5 | 百万级模糊搜索必须走索引，不能每次扫全表 |
| 多站合并关系 | SQLite | 需要按名字聚合、按时间排序、按分类过滤 |
| 采集进度 | SQLite | 需要事务内更新、按站点查询、断点续采 |
| 站点对账 | SQLite `cache_sites` | 启动时只读少量行，判断站点删除/地址变化 |
| 演员、标签（`vod_actor` / `vod_class`） | SQLite `videos` + `video_sources` | 来源级值存 `video_sources`，列表用的主来源聚合值存 `videos` |
| 详情缓存索引（路径、大小、缓存/访问时间、源快照、过期/错误） | SQLite `video_sources` | 详情页先查索引拿位置；容量统计用索引，不扫目录 |
| 详情正文（完整简介、播放线路、导演/地区/语言/状态） | 文件 JSON | 体积大、按整份读取、不参与 SQL 查询 |

关键收益：

- SQLite 不存 `dl`（播放地址）、完整简介等详情正文，只存轻量索引；库文件和 WAL 仍然远小于正文。
- 详情文件按需产生，只有用户看过的视频才有完整详情，不会在首次全量采集时写几百万个文件。
- 详情读取先查 SQLite 索引；命中直接读文件，未命中/文件丢失才实时抓取并回填索引，不需要每次猜路径或扫目录。
- 清理缓存时，SQLite 可以重建，详情目录可以整体删除，不需要百万行 `DELETE`。
- 启动时只打开 SQLite、读一张极小的 `cache_sites`，不遍历 `videos` 目录。
- 详情文件是普通 JSON，便于排查、迁移和后续压缩/归档。
- 容量统计用 `SUM(detail_size)` / 详情索引计数，不需要遍历详情目录；需要校对时再按需扫描。

代价：

- 详情索引存在，但文件可能被外部删除/改坏；读取和容量“扫描校对”仍需 `stat`/读取文件确认，索引不能单独保证文件存在。
- 索引与文件可能短暂不一致（例如写完文件、索引更新前崩溃）；读取时发现缺失会清索引并重新抓取，容量扫描可对账。
- 孤儿文件（进程在写文件与删除之间崩溃等）只能靠维护任务扫描目录清理。

## 5. SQLite 设计（缓存库 + 采集计划）

### 5.0 表清单（先确认）

现有业务库 `userData/Data/cine-box.db`（本次只新增 `collect_schedules`）：

| 表 | 作用 |
|---|---|
| `sites` | 采集站点 |
| `site_categories` | 站点在线分类 |
| `video_categories` | 本地视频分类 |
| `category_bindings` | 在线分类与本地分类的绑定 |
| `collect_schedules` | 定时采集计划（每个站点一条） |

缓存库 `userData/Data/video-cache.db`（本设计）：

| 表 | 类型 | 作用 |
|---|---|---|
| `videos` | 普通表 | 合并后的视频，列表/搜索/排序主表 |
| `video_sources` | 普通表 | 站点来源 + 列表字段 + 演员/标签 + 详情索引 + 全量替换标记；唯一键 `site_id + source_video_id` |
| `videos_fts` | FTS5 虚拟表 | 名称搜索；SQLite 会自动创建 `videos_fts_*` 影子表 |
| `cache_sites` | 普通表 | 启动时按站点对账，不随视频数增长 |
| `collect_progress` | 普通表 | 采集进度、全量替换计数，本次调整的对象 |
| `collect_logs` | 普通表 | 采集运行日志，控制台“日志”分区读取 |

`userData/Data/videos/` 是详情 JSON 文件目录，不是数据库表。

> `videos_fts_*` 影子表由 SQLite FTS5 自动管理，不手工建、不手工删；业务代码只操作 `videos` 和 `videos_fts`。
> `video-cache.db` 里没有独立详情表；详情索引是 `video_sources.detail_*` 字段，正文在 `Data/videos` 的 JSON 文件里。

### 5.1 `videos`：合并后的视频

```sql
CREATE TABLE IF NOT EXISTS videos (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL,
  name_key TEXT NOT NULL UNIQUE,
  search_text TEXT NOT NULL,
  latest_ts INTEGER NOT NULL DEFAULT 0,
  latest_time TEXT NOT NULL DEFAULT '',
  primary_source_id INTEGER,
  source_count INTEGER NOT NULL DEFAULT 0,
  pic TEXT NOT NULL DEFAULT '',
  note TEXT NOT NULL DEFAULT '',
  vod_actor TEXT NOT NULL DEFAULT '',
  vod_class TEXT NOT NULL DEFAULT '',
  intro_excerpt TEXT NOT NULL DEFAULT '',
  intro_truncated INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_videos_latest
  ON videos (latest_ts DESC, id DESC);
```

#### 5.1.1 身份与合并字段

| 字段 | 类型 | 作用 |
|---|---|---|
| `id` | `INTEGER PRIMARY KEY` | 合并后的规范视频 ID（SQLite rowid）。被 `video_sources.video_id` 引用；也是 `videos_fts` 的 `content_rowid`。来源更新时不变；当该视频没有任何来源时整行删除，之后同名视频会得到新的 ID。 |
| `name` | `TEXT NOT NULL` | **主来源的显示名**，用于列表、详情标题和 FTS 文本生成。不是所有来源名的集合；主来源变化时可能跟着变。 |
| `name_key` | `TEXT NOT NULL UNIQUE` | **名字合并键**，唯一索引。采集写入时按它查/建规范视频：`NFKC + 小写 + 去空白/零宽字符`。例如 `名侦探柯南（国语）` 与 `名侦探柯南(国语)` 会得到同一个 key。只用于合并，不用于展示。 |
| `source_count` | `INTEGER NOT NULL DEFAULT 0` | 该视频当前有多少个站点来源，等于 `video_sources` 中 `video_id = videos.id` 的行数。列表/详情可显示“N 个来源”；0 是过渡态，提交前会删除该规范视频。 |
| `primary_source_id` | `INTEGER` | 主来源的 `video_sources.id`。列表的封面、进度、原始分类都取这一行；详情页仍会列出全部来源。字段允许暂时为空（同一事务里先建 `videos` 再插来源），但一页提交后应始终指向一个存在的来源。 |

`id`、`name_key`、`source_count`、`primary_source_id` 的关系：

- 业务上“同一个视频”由 `name_key` 决定，不由 `id` 决定。
- 一个 `videos` 行可以有 1–N 个 `video_sources` 行；`source_count` 是 N。
- `primary_source_id` 是 N 行中被选中的那一行，不是 `videos.id` 的副本。

示例：

```text
videos:
id=1  name=名侦探柯南  name_key=名侦探柯南
      source_count=2  primary_source_id=11
      vod_actor=演员甲,演员乙  vod_class=动作,冒险

video_sources:
id=11  site_id=A  source_video_id=1001  video_id=1  note=更新至第120集
id=12  site_id=B  source_video_id=8899  video_id=1  note=更新至第118集
```

#### 5.1.2 搜索字段

| 字段 | 类型 | 作用 |
|---|---|---|
| `search_text` | `TEXT NOT NULL` | FTS5 专用文本，不用于展示。由 `name` 生成：汉字逐字加空格，拉丁/数字按词保留，其余字符转空格。例如 `名侦探柯南` → `名 侦 探 柯 南`，`Spider-Man 蜘蛛侠` → `spider man 蜘 蛛 侠`。 |

- `videos_fts` 是 `search_text` 的外部内容 FTS5 表，`content_rowid = videos.id`。
- `videos` 插入/删除/`search_text` 更新时由触发器同步到 `videos_fts`。
- `search_text` 只在 `name` 真正变化时重写；避免无意义地重建 FTS 索引。
- 搜索只查名称，不查演员/导演/简介；后续要扩搜需另加字段或索引。

#### 5.1.3 排序与主来源字段

| 字段 | 类型 | 作用 |
|---|---|---|
| `latest_ts` | `INTEGER NOT NULL DEFAULT 0` | 该视频所有来源 `source_ts` 的最大值（epoch ms）。列表默认按 `latest_ts DESC, id DESC` 排序；键集分页依赖 `idx_videos_latest`。 |
| `latest_time` | `TEXT NOT NULL DEFAULT ''` | 主来源的原始更新时间文本，用于展示。正常情况下主来源就是 `source_ts` 最大的来源，所以它与 `latest_ts` 对应；站点未返回时间时可能为空。 |
| `primary_source_id` | `INTEGER` | 主来源选择规则：按 `source_ts DESC, id ASC` 取第一条。最近更新的来源优先；时间相同则来源行 ID 小的优先，保证结果稳定。 |

重算规则：

- 来源新增/更新/删除后，只重算受影响的 `video_id`。
- `latest_ts = MAX(video_sources.source_ts WHERE video_id = ?)`。
- `primary_source_id` 取 `ORDER BY source_ts DESC, id ASC LIMIT 1`。
- 主来源被删除或改名迁走时，`primary_source_id` 自动切到下一个来源；列表封面/进度随之变化。
- 没有任何来源时删除 `videos` 行，FTS 触发器同步删除。

#### 5.1.4 列表展示与来源聚合字段

这些字段是“主来源优先 + 空值回退”的聚合结果。列表读取这些字段时不用逐行 join 所有来源；分类/站点仍通过 `primary_source_id` join 主来源一行。

| 字段 | 类型 | 作用 |
|---|---|---|
| `pic` | `TEXT` | 主来源封面 URL。主来源为空时，回退到按 `source_ts DESC, id ASC` 排序的第一个非空封面。 |
| `note` | `TEXT` | 主来源更新进度，如“更新至第07集”“已完结”。主来源为空时同样回退到第一个非空 `note`。 |
| `vod_actor` | `TEXT` | 主来源的主演/演员文本；主来源为空时回退到第一个非空来源。逐来源的完整值仍在 `video_sources.vod_actor`。 |
| `vod_class` | `TEXT` | 主来源的标签/剧情分类文本；主来源为空时回退到第一个非空来源。逐来源的完整值仍在 `video_sources.vod_class`。 |
| `intro_excerpt` | `TEXT` | 主来源的列表简介摘要，最多 160 字；列表展示用。完整简介不在这里，在详情 JSON 文件里。 |
| `intro_truncated` | `INTEGER` | 摘要是否被截断（0/1）。列表显示省略号用；如果主来源没有摘要，回退到第一个非空摘要并同步该标记。 |

回退顺序统一为：

```text
主来源（primary_source_id） → 其余来源按 source_ts DESC, id ASC → 空值
```

主来源变化时，这些字段可能一起变化；重算时只在值真正变化时刷新 `updated_at`。演员/标签只是“列表用的聚合值”，按站点查看完整值仍走 `video_sources` 或详情页。

#### 5.1.5 时间戳字段

| 字段 | 类型 | 作用 |
|---|---|---|
| `created_at` | `TEXT` | 该规范视频第一次创建的时间（ISO 8601）。后续来源合并、主来源切换都不改它。 |
| `updated_at` | `TEXT` | 聚合字段最后一次**真正变化**的时间。只有 `name / search_text / latest_ts / latest_time / primary_source_id / source_count / pic / note / vod_actor / vod_class / intro_excerpt / intro_truncated` 发生变化时才刷新；单纯来源被标记（如 `last_full_run`）不算。 |

`updated_at` 不用于列表排序；列表排序用 `latest_ts`（站点更新时间），两者不要混用。

#### 5.1.6 写入与重算流程

1. 采集一页解析出 `VideoInput[]`，每条算 `name_key`。
2. 按 `name_key` 查 `videos`：
   - 不存在 → 插入占位行（`name`、`name_key`、`search_text`、时间戳），FTS 触发器插入索引；
   - 存在 → 复用。
3. 按 `(site_id, source_video_id)` upsert `video_sources`：
   - 新来源 → 指向第 2 步的 `video_id`；
   - 已有来源但改名导致 `name_key` 变化 → 更新 `video_id`，旧规范视频加入待重算集合。
4. 本页结束后，对受影响的 `video_id` 逐个重算：
   - 取全部来源，按 `source_ts DESC, id ASC` 排序；
   - 无来源 → `DELETE FROM videos`（FTS 同步删除）；
   - 有来源 → 更新 `latest_ts / latest_time / primary_source_id / source_count / name / search_text / pic / note / vod_actor / vod_class / intro_excerpt / intro_truncated`；
   - `name`/`search_text` 没变时不要写这两列，避免触发无意义的 FTS 重建；
   - 其它聚合字段都没变时不要刷新 `updated_at`。
5. 来源改名迁走后，旧 `videos` 若已无来源会删除；新 `videos` 若不存在会在第 2 步创建。

#### 5.1.7 这张表不存什么

- **不存站点 ID、站点名、原始分类 ID/名称**：这些在 `video_sources`，列表通过 `primary_source_id` join 取。
- **不存绑定分类路径**：读时按主来源的 `(site_id, category_id)` 反查 `category_bindings` / `video_categories`。
- **不存逐来源的演员/标签完整集合**：`videos` 只保留“主来源优先”的聚合值；每个来源的完整演员/标签在 `video_sources.vod_actor` / `vod_class`。完整简介、播放线路、导演在 `Data/videos/<siteId>/<sourceVideoId>.json`。
- **不存详情缓存状态**：详情索引在 `video_sources.detail_*`，`videos` 不重复保存；详情正文在 JSON 文件。
- **不存 `last_full_run`**：全量替换标记在 `video_sources`，因为它是来源级状态，不是合并视频级状态。
- **不存采集进度**：在 `collect_progress`。

#### 5.1.8 索引

| 索引 | 作用 |
|---|---|
| `UNIQUE (name_key)` 自动索引 | 采集按名字查/建规范视频；保证同名只合并成一行 |
| `idx_videos_latest (latest_ts DESC, id DESC)` | 列表默认时间倒序 + 键集分页；也用于 `latest_ts` 相同情况下按 `id` 兜底排序 |
| `videos_fts`（FTS5） | 名称模糊搜索；与 `videos` 通过 `content_rowid = id` 关联 |

### 5.2 `video_sources`：站点来源 + 列表字段 + 演员/标签 + 详情索引 + 全量替换标记

  id INTEGER PRIMARY KEY,

#### 5.2.1 身份与关联字段

| 字段 | 类型 | 作用 |
|---|---|---|
| `id` | `INTEGER PRIMARY KEY` | 本表内部行 ID（代理键），被 `videos.primary_source_id` 引用。来源更新时保持不变；来源删除后重新插入会得到新 ID，因此删来源后必须重算 `primary_source_id`。 |
| `site_id` | `TEXT NOT NULL` | 采集站点 ID，对应业务库 `sites.id`。与 `source_video_id` 一起构成业务唯一键；也用于按站点删除缓存、分类绑定反查、推导详情文件目录。缓存库与业务库是两个 SQLite 文件，所以这里没有外键，站点删除由 `cache_sites` 对账和 `removeSite` 显式清理。 |
| `source_video_id` | `TEXT NOT NULL` | 采集站返回的视频 ID（`vod_id` / `<id>`）。全程字符串，18 位 ID 不转 Number，避免精度丢失；同时是详情文件名的一部分。 |
| `video_id` | `INTEGER NOT NULL` | 指向合并后的 `videos.id`，外键 `ON DELETE CASCADE`。多个站点来源可以指向同一个 `video_id`，列表只显示一条合并视频；详情页按 `video_id` 查出全部来源。来源改名时该字段会迁移到新的规范视频。 |

业务唯一键是 `(site_id, source_video_id)`，不是 `id`；`id` 只服务于 SQLite 内部关联和 `primary_source_id`。

示例：

```text
videos:
id=1  name=名侦探柯南  primary_source_id=11

video_sources:
id=11  site_id=A  source_video_id=1001  video_id=1
       vod_actor=演员甲,演员乙  vod_class=动作,冒险
id=12  site_id=B  source_video_id=8899  video_id=1
       vod_actor=演员甲  vod_class=动作
```

`id=11` 和 `id=12` 是同名视频在两个站点的两条来源，业务唯一键分别是 `(A, 1001)`、`(B, 8899)`。

#### 5.2.2 列表展示字段

| 字段 | 类型 | 作用 |
|---|---|---|
| `name` | `TEXT NOT NULL` | 该站点自己的视频名。采集写入时用它计算 `name_key`；该来源成为主来源时，名称会同步到 `videos.name`。 |
| `pic` | `TEXT` | 该站点封面 URL。列表取主来源封面；主来源为空时回退到其它来源。 |
| `note` | `TEXT` | 更新进度，如“更新至第07集”“已完结”。列表显示；详情过期判断也会和详情文件里的 `note` 对比。 |
| `intro_excerpt` | `TEXT` | 列表用简介摘要，最多 160 字。详情正文不在这里，在详情 JSON 文件里。 |
| `intro_truncated` | `INTEGER` | 摘要是否被截断（0/1）。列表显示省略号用。 |

列表页只读这些字段和 `videos` 的聚合字段，不读详情文件。

#### 5.2.3 时间字段

| 字段 | 类型 | 作用 |
|---|---|---|
| `source_time` | `TEXT` | 站点返回的原始更新时间文本，如 `2026-11-16 12:00:00`。用于展示和排查。 |
| `source_ts` | `INTEGER` | `source_time` 解析后的 epoch 毫秒。用于排序、选主来源、详情是否过期、全量替换删除条件；解析失败时用旧值或入库时间兜底。 |
| `created_at` | `TEXT` | 该来源第一次插入的时间（ISO 8601）。 |
| `updated_at` | `TEXT` | 列表字段最后一次**真正变化**的时间。`full + all` 只写 `last_full_run` 时不要刷新它，避免“标记更新”被误认为内容更新。 |

`source_time` 是展示值，`source_ts` 是计算值，两个都保留。

#### 5.2.4 分类字段

| 字段 | 类型 | 作用 |
|---|---|---|
| `category_id` | `TEXT` | 采集站原始分类 ID（`tid` / `type_id`），如 `59`。用于反查绑定：`(site_id, category_id)` → `site_categories` → `category_bindings`。 |
| `category_name` | `TEXT` | 采集站原始分类名快照，如“动漫”“动作片”。未绑定或站点分类已删除时用于兜底显示；已绑定时优先显示本地分类路径。 |

列表显示规则：

- 未绑定：显示 `category_name` + `category_id`。
- 已绑定：显示 `video_categories` 里的本地分类路径，原始分类保留在字段里供 tooltip。
- 绑定关系变化不需要重采，下一次读取重新 join 即可。

#### 5.2.5 来源扩展字段

| 字段 | 类型 | 作用 |
|---|---|---|
| `vod_actor` | `TEXT` | 采集站原始主演/演员文本，通常是逗号分隔的多个人名。列表读 `videos.vod_actor` 聚合值，详情按来源展示；当前不参与搜索索引。写入时截断到 1000 字。 |
| `vod_class` | `TEXT` | 采集站原始 `vod_class` 标签/剧情分类文本，可能是一个或多个标签。列表读 `videos.vod_class` 聚合值，详情按来源展示。它和 `category_id` / `category_name`（`type_id` / `type_name`）不是一回事：后者是站点分类，前者是视频自身的标签/题材。写入时截断到 500 字。 |

- 两个字段都是**来源级**数据：不同站点可以给同一视频不同的演员表和标签。
- 会聚合到 `videos.vod_actor` / `videos.vod_class`（主来源优先、空值回退），列表直接读聚合值；逐来源完整值仍在本表，详情页列出全部来源。
- 写入策略：新值为空时保留旧值，非空时覆盖；避免站点偶发不返回这两个字段时把已有数据冲掉。
- 不进入 FTS 搜索；当前不建索引，后续要按演员/标签筛选再单独加索引或搜索表。

#### 5.2.6 详情缓存索引字段

| 字段 | 类型 | 作用 |
|---|---|---|
| `detail_path` | `TEXT` | 详情文件相对路径，如 `siteId/12345.json`；空表示没有索引/未缓存。 |
| `detail_size` | `INTEGER` | 详情文件字节数；容量统计 `SUM(detail_size)` 用。 |
| `detail_cached_at` | `TEXT` | 详情文件写入成功时间（ISO 8601）；空表示未缓存。 |
| `detail_accessed_at` | `TEXT` | 最近一次读取详情的时间；读取命中时限流更新（例如 1 小时一次），供后续 LRU/清理参考。 |
| `detail_source_ts` | `INTEGER` | 写文件时来源的 `source_ts` 快照；列表同步发现 `source_ts` 变化时置 `detail_stale = 1`。 |
| `detail_note` | `TEXT` | 写文件时来源的 `note` 快照；用于判断更新进度是否变化。 |
| `detail_stale` | `INTEGER` | 0/1；列表同步发现来源更新过，详情文件可能过期。读取时仍可返回旧详情并带 `detailStale`，由刷新接口更新。 |
| `detail_error` | `TEXT` | 最近一次详情抓取/读写错误；空表示正常。文件不存在/损坏时也会记录。 |

约定：

- **只存索引，不存正文**：路径、大小、时间、状态在这里，完整简介/播放线路/导演仍在详情 JSON 文件。
- 写详情：先写文件（临时文件 + rename），成功后再更新这些列；失败只写 `detail_error`，不把索引标成可用。
- 读详情：先看 `detail_cached_at` / `detail_path`；有索引就按路径读文件，读不到或损坏则清空索引并实时抓取；成功后再回填索引。
- 命中读取时更新 `detail_accessed_at`（限流），不每次都写库。
- 列表同步：来源 `source_ts`/`note` 与快照不一致时置 `detail_stale = 1`，不改文件。
- 详情清理：删除文件后把这些列重置为空/0。
- 容量统计：`COUNT(*) WHERE detail_cached_at <> ''`、`SUM(detail_size)`，走部分索引，不扫目录。

#### 5.2.7 全量替换字段

| 字段 | 类型 | 作用 |
|---|---|---|
| `last_full_run` | `TEXT` | 最近一次 `full + all` 采集“看到过该来源”的运行 token，值就是 `collect_progress.started_at`。整轮成功完成后用它找出并删除本次未返回的旧来源；其它模式（增量 24h/48h）不改它。 |

工作方式：

1. `full + all` 每页 upsert 时，无论列表字段是否变化，都写 `last_full_run = 当前 runToken`。
2. 整轮完整跑完后，删除：

```sql
DELETE FROM video_sources
WHERE site_id = ?
  AND last_full_run <> 当前 runToken
  AND source_ts <= runStartTs;
```

3. 其它模式不动 `last_full_run`，所以增量新增的来源是 `''`，下一次全量会重新标记。
4. 未完整结束（暂停/取消/错误/达到 `maxPages`）不执行删除。

#### 5.2.8 唯一约束与索引

| 约束 / 索引 | 作用 |
|---|---|
| `UNIQUE (site_id, source_video_id)` 自动索引 | 采集 upsert、按来源定位、详情文件路径推导；同一站点同一视频 ID 只允许一行 |
| `idx_video_sources_video (video_id)` | 详情页查某合并视频的全部来源；删来源后按 `video_id` 重算 |
| `idx_video_sources_category (site_id, category_id)` | 按站点分类筛选、分类绑定反查 |
| `idx_video_sources_site_time (site_id, source_ts DESC)` | 按站点/时间查询、全量替换候选 |
| `idx_video_sources_full_run (site_id, last_full_run, source_ts)` | 全量替换时找“本次没看到的旧来源” |
| `idx_video_sources_detail (site_id, detail_cached_at, detail_size) WHERE detail_cached_at <> ''` | 详情索引查询、按站点容量统计；只覆盖已缓存详情 |

#### 5.2.9 这张表不存什么

- **不存完整简介、播放线路、导演**：完整简介和播放线路在 `Data/videos/<siteId>/<sourceVideoId>.json`；导演也只在详情文件里。演员和标签已经存在本表的 `vod_actor` / `vod_class`。
- **不存详情正文**：路径、大小、缓存时间、访问时间、过期/错误是索引字段，存在本表；正文在 JSON 文件。
- **不存 `name_key`**：合并键在 `videos.name_key`。
- **不存绑定分类名/路径**：读时 join `category_bindings` / `video_categories`。
- **不存站点显示名**：读时从 `sites` 取。
- **不存采集进度**：在 `collect_progress`。

### 5.3 `cache_sites`：启动对账

```sql
CREATE TABLE IF NOT EXISTS cache_sites (
  site_id TEXT PRIMARY KEY,
  address TEXT NOT NULL DEFAULT '',
  format TEXT NOT NULL DEFAULT '',
  updated_at TEXT NOT NULL
);
```

- 每个缓存过的站点一行，采集开始时 upsert，不随视频数增长。
- 启动时只读这张表，与 `sites` 表对比：
  - 站点已删除；
  - 站点地址或 XML/JSON 格式变化。
- 命中以上情况才调用 `removeSite(site_id)`，删除来源、进度和 `Data/videos/<siteId>` 目录。
- 这样启动**不需要** `SELECT DISTINCT site_id FROM video_sources`，缓存库再大也不会在启动时扫大表。

### 5.4 `collect_progress`：采集进度

```sql
CREATE TABLE IF NOT EXISTS collect_progress (
  id TEXT PRIMARY KEY,                -- `${site_id}:${mode}:${fetch_range}`
  site_id TEXT NOT NULL,
  mode TEXT NOT NULL
    CHECK (mode IN ('incremental', 'full')),
  fetch_range TEXT NOT NULL DEFAULT 'all'
    CHECK (fetch_range IN ('all', '24h', '48h')),
  status TEXT NOT NULL DEFAULT 'idle'
    CHECK (status IN ('idle', 'queued', 'running', 'paused', 'replacing', 'done', 'error')),
  page INTEGER NOT NULL DEFAULT 0,
  page_count INTEGER NOT NULL DEFAULT 0,
  record_count INTEGER NOT NULL DEFAULT 0,
  page_size INTEGER NOT NULL DEFAULT 0,
  fetched INTEGER NOT NULL DEFAULT 0,
  inserted INTEGER NOT NULL DEFAULT 0,
  updated INTEGER NOT NULL DEFAULT 0,
  failed INTEGER NOT NULL DEFAULT 0,
  deleted INTEGER NOT NULL DEFAULT 0,   -- full + all 全量替换时删掉的旧来源数
  error TEXT NOT NULL DEFAULT '',
  started_at TEXT NOT NULL DEFAULT '',
  finished_at TEXT NOT NULL DEFAULT '',
  updated_at TEXT NOT NULL,

  UNIQUE (site_id, mode, fetch_range)
);

CREATE INDEX IF NOT EXISTS idx_collect_progress_site
  ON collect_progress (site_id, updated_at DESC);
```

#### 5.4.1 字段说明

| 字段 | 含义 | 写入时机 |
|---|---|---|
| `id` | 任务唯一键：`${site_id}:${mode}:${fetch_range}` | 创建任务时 |
| `site_id` | 采集站点 ID（32 位十六进制） | 创建任务时 |
| `mode` | 采集模式：`full` 全量 / `incremental` 增量 | 创建任务时 |
| `fetch_range` | 采集方式：`all` 全量 / `24h` 24 小时内 / `48h` 48 小时内 | 创建任务时 |
| `status` | `idle` 未开始、`queued` 已入队等待、`running` 进行中、`paused` 已暂停、`replacing` 正在全量替换、`done` 已完成、`error` 出错 | 状态变化时 |
| `page` | **最后一次成功提交**的页码；0 表示还没有成功页 | 每页提交后 |
| `page_count` | 站点本次返回的总页数（`pagecount`） | 每页响应后 |
| `record_count` | 站点本次返回的总记录数（`recordcount`），是整个站点/采集范围的总量，不是已处理量 | 每页响应后 |
| `page_size` | 站点**实际生效**的每页条数（回读 `pagesize` / `limit`），不是请求的 100 | 每页响应后 |
| `fetched` | 本次任务累计从响应中成功解析出的记录数；包含后面因字段缺失被跳过的记录，不包含整页请求失败的记录 | 每页提交后累加 |
| `inserted` | 其中在 `video_sources` 中**新建**的来源行数（按 `site_id + source_video_id` 判断），不是 `videos` 新增行数 | 每页提交后累加 |
| `updated` | 其中命中**已有来源行**且至少一个列表字段发生变化的行数 | 每页提交后累加 |
| `failed` | 其中因缺少 `source_video_id` / `name` 等必要字段而未写入的行数 | 每页提交后累加 |
| `deleted` | `full + all` 全量替换时，删掉的“本次未返回”的旧来源行数；其它模式保持 0 | 替换清理阶段累加 |
| `error` | 最近一次错误或替换警告（截断保存）；成功开始时清空 | 出错时 / 新任务时清空 |
| `started_at` | 本次任务开始时间；续采保留原值，重新开始/`restart` 时重置；`full + all` 同时作为 `last_full_run` 的运行 token | 新任务/续采 |
| `finished_at` | 本次任务进入终态（`done` / `error`）的时间；暂停时不写；`done` 时同时作为“上次成功同步时间” | 终态时 |
| `updated_at` | 这一行最后一次写入时间，用于 UI 判断进度是否还在更新 | 每次进度写入 |

**主键说明**：已确认采用 `site_id + mode + fetch_range`，让“全量 / 24h / 48h”三种采集方式与增量/全量两种模式各自保留进度；如果只用 `site_id + mode`，三种采集方式会互相覆盖。

**`mode` 与 `fetch_range` 的组合**：

| `mode` | `fetch_range` | 说明 |
|---|---|---|
| `full` | `all` | 全量翻页（第 1 页到 `page_count`），逐页 upsert；整轮成功完成后执行**全量替换**：删除本次未返回的旧来源 |
| `incremental` | `24h` | 请求 `h=24`，翻页 upsert 最近 24 小时更新的数据；不删除旧来源 |
| `incremental` | `48h` | 请求 `h=48`，翻页 upsert 最近 48 小时更新的数据；不删除旧来源 |
| `incremental` | `all` | 不推荐/建议禁止：等同全量翻页 + upsert，没有“追平”截止点，耗时与 `full + all` 相同，但不会触发全量替换 |
| `full` | `24h` / `48h` | 不允许：全量模式只对全量范围有意义 |

> 已确认：主键用 `site_id + mode + fetch_range`；本表只保留“当前进度/最后一次运行”，不保留历史；`full + all` 需要全量替换。全量替换的具体安全规则见 10.4。

> 相比最初的字段清单，额外增加了两个字段/状态：`deleted`（全量替换删除了多少旧来源）和 `status = replacing`（正在替换，页面/进度可单独展示）。如果不需要展示替换过程，可以去掉，但 `full + all` 的删除结果就没有计数可查。

> 去掉 `last_sync_at` 后，增量模式不再靠“上次同步时间”判断追平，而是靠 `fetch_range` 的 `h=24/48` 限制范围。如果后续确实需要“增量 + 全量范围”，要么恢复 `last_sync_at`，要么单独加一张同步状态表；当前不推荐这种组合。

#### 5.4.2 计数器语义

`fetched` 是“本次任务处理了多少条”，不是站点总量，也不等于 `record_count`。每成功提交一页，按以下方式累加：

```text
fetched   += 本页解析出的记录数
inserted  += 本页中 (site_id, source_video_id) 原来不存在的记录数
updated   += 本页中原来已存在、且列表字段真正发生变化的记录数
failed    += 本页中 missing source_video_id / name 等未写入的记录数
unchanged  = fetched - inserted - updated - failed   （不落库，按需计算）
```

- 一页 100 条、20 条新来源、30 条有变化、45 条无变化、5 条缺名字：
  `fetched = 100`、`inserted = 20`、`updated = 30`、`failed = 5`，可算出 `unchanged = 45`。
- `inserted` 统计的是**来源行**，不是合并后的 `videos` 行：新站点加入一个已存在名字的视频，`inserted` 仍 +1，但 `videos` 不会新增。
- `updated` 只统计**列表字段实际变化**（`name/pic/note/intro_excerpt/source_time/source_ts/category_id/category_name/vod_actor/vod_class` 等）；只是命中已有行但值没变，不算 `updated`，算 `unchanged`。
- 整页请求失败/解析失败：不增加 `fetched`，不推进 `page`，只写 `error`。
- 计数器是**当前任务累计值**：从 `paused/error` 续采时保留并继续累加；`done` 后重新开始或 `restart` 时清零。
- 详情刷新不写这张表；详情错误在读取/刷新详情时按文件现场判断。

### 5.5 FTS 索引

```sql
CREATE VIRTUAL TABLE IF NOT EXISTS videos_fts USING fts5(
  search_text,
  content='videos',
  content_rowid='id',
  tokenize='unicode61 remove_diacritics 2'
);

CREATE TRIGGER IF NOT EXISTS videos_ai AFTER INSERT ON videos BEGIN
  INSERT INTO videos_fts(rowid, search_text) VALUES (new.id, new.search_text);
END;

CREATE TRIGGER IF NOT EXISTS videos_ad AFTER DELETE ON videos BEGIN
  INSERT INTO videos_fts(videos_fts, rowid, search_text)
  VALUES ('delete', old.id, old.search_text);
END;

CREATE TRIGGER IF NOT EXISTS videos_au AFTER UPDATE OF search_text ON videos BEGIN
  INSERT INTO videos_fts(videos_fts, rowid, search_text)
  VALUES ('delete', old.id, old.search_text);
  INSERT INTO videos_fts(rowid, search_text) VALUES (new.id, new.search_text);
END;
```

`search_text` 构造：

- 汉字逐字加空格：`名侦探柯南` → `名 侦 探 柯 南`
- 拉丁/数字按词保留：`Spider-Man 蜘蛛侠` → `spider man 蜘 蛛 侠`
- NFKC、转小写、折叠空白，其它字符转空格。

查询构造：

- 连续汉字 → 短语 `"柯 南"`，保证相邻。
- 拉丁/数字 → 前缀词 `spider*`。
- 混合查询 → 空格连接，FTS 隐式 AND。
- 过滤 FTS 语法字符；查询作为绑定参数传入，不拼 SQL。

这样 1 字、2 字、3+ 字中文都能走 FTS 索引，不需要 `LIKE '%词%'`。

### 5.6 `collect_schedules`：定时采集计划（业务库 `cine-box.db`）

定时采集属于用户配置，不是可丢弃缓存，因此放在业务库，而不是 `video-cache.db`；清空视频缓存不会丢计划，备份也能带走。

```sql
CREATE TABLE IF NOT EXISTS collect_schedules (
  site_id TEXT PRIMARY KEY REFERENCES sites (id) ON DELETE CASCADE,
  mode TEXT NOT NULL
    CHECK (mode IN ('incremental', 'full')),
  fetch_range TEXT NOT NULL DEFAULT '24h'
    CHECK (fetch_range IN ('all', '24h', '48h')),
  interval_minutes INTEGER NOT NULL DEFAULT 360
    CHECK (interval_minutes >= 5),
  enabled INTEGER NOT NULL DEFAULT 1,
  next_run_at TEXT NOT NULL DEFAULT '',   -- ISO 8601 UTC
  last_run_at TEXT NOT NULL DEFAULT '',
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_collect_schedules_due
  ON collect_schedules (enabled, next_run_at);
```

| 字段 | 作用 |
|---|---|
| `site_id` | 主键，一个站点一条计划；删站点时外键级联删除 |
| `mode` | `incremental` / `full`，与 `collect_progress.mode` 一致 |
| `fetch_range` | `all` / `24h` / `48h`，与 `collect_progress.fetch_range` 一致 |
| `interval_minutes` | 间隔分钟数，最小 5；UI 提供 30 分钟、1/3/6/12/24 小时等快捷值 |
| `enabled` | 是否启用定时 |
| `next_run_at` | 下次计划运行时间；禁用时为空 |
| `last_run_at` | 上次计划触发时间 |
| `created_at` / `updated_at` | 记录时间 |

约定：

- 本版**一个站点一条计划**。如果以后需要“同一站点同时跑 24h 频繁 + 全量每周”，把主键改成 `id`，再加 `UNIQUE (site_id, mode, fetch_range)`。
- 保存/启用计划时：`next_run_at = now + interval_minutes`；禁用时 `next_run_at = ''`。
- 应用启动时读取启用的计划；如果 `next_run_at` 已过期，只补跑一次，然后把 `next_run_at` 推到 `now + interval`，避免停机后连续补跑。
- 计划触发只负责“入队”，真正执行仍走单队列采集器；同一 `(site_id, mode, fetch_range)` 已在运行/排队时跳过并记日志。
- 计划保存后，即使采集失败也按间隔继续下一次；错误写日志和 `collect_progress.error`。

### 5.7 `collect_logs`：采集日志（缓存库 `video-cache.db`）

```sql
CREATE TABLE IF NOT EXISTS collect_logs (
  id INTEGER PRIMARY KEY,
  created_at TEXT NOT NULL,
  level TEXT NOT NULL
    CHECK (level IN ('info', 'warn', 'error')),
  site_id TEXT NOT NULL DEFAULT '',
  mode TEXT NOT NULL DEFAULT '',
  fetch_range TEXT NOT NULL DEFAULT '',
  message TEXT NOT NULL,
  detail TEXT NOT NULL DEFAULT ''
);

CREATE INDEX IF NOT EXISTS idx_collect_logs_created
  ON collect_logs (created_at DESC, id DESC);

CREATE INDEX IF NOT EXISTS idx_collect_logs_site
  ON collect_logs (site_id, created_at DESC);
```

| 字段 | 作用 |
|---|---|
| `id` | 自增行号，日志分页/游标用 |
| `created_at` | 日志时间（ISO 8601） |
| `level` | `info` / `warn` / `error` |
| `site_id` / `mode` / `fetch_range` | 关联的采集任务；手动/定时都写 |
| `message` | 简短中文描述，截断 500 字 |
| `detail` | 错误详情、HTTP 状态、重试次数等，截断 2000 字 |

约定：

- 日志属于诊断数据，不进入备份；`videos:clear` 重建缓存库时会一并清空。
- 保留策略：最多 5000 行或 30 天，先到先删；启动时和每写入 100 行时执行一次裁剪。
- 不是每一页都写日志：开始、每 10 页、完成、取消、错误、重试、全量替换阶段各写一条，避免百万页把日志表打爆。
- 控制台“日志”分区通过 `videos:logs:list` 分页读取，通过 `videos:logs:onAppend` 实时追加。

## 6. 详情文件缓存

### 6.1 目录与命名

```text
userData/Data/videos/
  <siteId>/
    <safeSourceVideoId>.json
```

- `siteId`：现有站点的 32 位十六进制 ID，本身安全。
- `safeSourceVideoId`：
  - 满足 `^[A-Za-z0-9_-]{1,100}$` 时直接使用；
  - 否则用 `sha1(sourceVideoId)` 的前 32 位十六进制；
  - 不允许 `.`、`..`、`/`、`\`、`:` 等路径字符。
- 路径由 `(site_id, source_video_id)` 推导，并在缓存成功时写入 `video_sources.detail_path`；读取时优先用索引里的相对路径，不每次重算。
- 读取前把 `detail_path`（或重新推导的路径）拼到根目录并 `resolve`，校验结果仍在根目录下，防止路径穿越。
- `detail_path` 为空、文件不存在或路径非法时，按 `(site_id, source_video_id)` 重新推导并实时抓取，成功后再回填索引。

> 一个来源一个文件，而不是一个合并视频一个文件。原因：唯一性本来就是 `siteId + sourceVideoId`；来源更新只重写自己的文件；详情页按来源汇总，互不覆盖。
>
> 如果未来单站点详情文件超过十万个，可以按 `safeSourceVideoId` 的哈希前缀再分一层目录。路径推导函数集中在一处；调整后新写入更新 `detail_path`，旧索引按新规则重新推导/迁移即可。

### 6.2 文件内容

```json
{
  "format": "cine-box-video-detail",
  "version": 1,
  "siteId": "a1b2c3d4e5f6...",
  "sourceVideoId": "12345",
  "fetchedAt": "2026-11-18T00:00:00.000Z",
  "sourceTime": "2026-11-16 12:00:00",
  "sourceTs": 1763265600000,
  "name": "示例视频",
  "pic": "https://example.com/pic.jpg",
  "note": "更新至第07集",
  "intro": "完整简介……",
  "state": "7",
  "year": "2026",
  "area": "中国大陆",
  "lang": "国语",
  "actor": "演员甲,演员乙",
  "vodClass": "动作,冒险",
  "director": "导演甲",
  "category": { "id": "59", "name": "动作片" },
  "playLines": [
    {
      "flag": "m3u8",
      "episodes": [
        { "name": "第01集", "url": "https://example.com/1/index.m3u8" },
        { "name": "第02集", "url": "https://example.com/2/index.m3u8" }
      ]
    }
  ]
}
```

说明：

- `sourceTs` / `note` 是详情缓存时的列表快照，用于读取时判断是否过期。
- `name` / `pic` / `note` / `category` / `actor` / `vodClass` 也写入文件，便于文件自包含和排查；**详情页读取时以 SQLite 的列表字段为准**（包括 `vod_actor` / `vod_class`），文件只提供详情专属字段（完整简介、播放线路、导演/地区/语言/状态）。
- 文件格式带 `format` + `version`，读取时校验；未来加字段走版本兼容。
- 读取时校验 `siteId` / `sourceVideoId` 与期望值一致，防止文件被错放或复制。
- 简介存纯文本（写入前已去 HTML/实体），渲染层必须按文本展示，不能用 `dangerouslySetInnerHTML`。
- 播放地址原样保存，渲染/播放前由上层校验协议；缓存层不执行 URL。

### 6.3 大小限制

- 单文件上限：`2 MiB`。
- 完整简介上限：`8000` 字。
- 单线路分集上限：`5000` 集。
- 序列化后超过 2 MiB 时：
  1. 先把简介截到 2000 字；
  2. 再把每条线路的分集截到 2000 集；
  3. 仍超限则放弃写详情文件，返回 `TOO_LARGE`，保留列表数据和旧详情（如果有）。
- 这些上限是安全阀，正常站点远低于此。

### 6.4 原子写入

详情写入 = **写文件 + 回填 SQLite 索引**：

1. 写到同目录临时文件：`<name>.json.tmp-<random>`。
2. `rename` 覆盖目标文件；Windows 上若目标被占用导致失败，先删除目标再重命名（概率低，失败则报错）。
3. 文件成功后更新 `video_sources`：
   - `detail_path` = 相对路径；
   - `detail_size` = 文件字节数；
   - `detail_cached_at` = 当前时间；
   - `detail_accessed_at` = 当前时间；
   - `detail_source_ts` / `detail_note` = 本次来源快照；
   - `detail_stale = 0`、`detail_error = ''`。
4. 文件失败：保留旧索引/旧文件，写 `detail_error`，返回 `FILE_WRITE_FAILED`。
5. 索引更新失败：文件可能成为孤儿；旧索引仍指向旧路径/旧状态。下次读取会因索引缺失/文件不匹配重新抓取，容量扫描可清理孤儿。

因为 `rename` 是原子的，读取方要么看到旧文件，要么看到新文件，不会读到半截 JSON。进程在临时文件写完、rename 之前崩溃，只会留下 `.tmp-*` 孤儿文件；索引仍是旧状态，下次读取会重新校验。

### 6.5 详情读取（索引优先 + 未命中实时抓取）

```text
videos:detail(videoId, { autoFetch = true })
  ├─ SELECT videos + 该视频全部 video_sources（含 detail_* 索引）
  ├─ 对每个 source：
  │    ├─ detail_cached_at = '' 或 detail_path = ''
  │    │    → 索引未命中：实时抓取该来源详情
  │    ├─ 有索引：按 detail_path 读文件
  │    │    ├─ 文件不存在 → 清空索引 → 实时抓取
  │    │    ├─ 解析失败/格式不符 → detail_error=FILE_CORRUPT → 清空索引 → 实时抓取
  │    │    └─ 读取成功 → detailAvailable=true，返回缓存
  │    ├─ 抓取成功 → 写文件 + 回填索引 → 返回本次详情
  │    └─ 抓取失败 → detailAvailable=false，detail_error 记录原因
  └─ 返回合并后的详情
```

规则：

- **索引存在且文件有效：不请求站点**，直接读文件；命中时更新 `detail_accessed_at`（限流，例如 1 小时一次）。
- **索引不存在/文件丢失/文件损坏：先实时抓取**，写文件并回填索引，再用本次结果返回；下一次打开直接走缓存。
- 多个来源同时未命中时，按站点分组、每批最多 10 个 `sourceVideoId` 请求，再逐一写文件/回填索引。
- 索引里的 `detail_stale = 1` 不触发自动抓取，仍返回旧详情并带 `detailStale`；由 `videos:detail:refresh` 显式刷新。
- 同一来源的并发抓取用 `Map<siteId:sourceVideoId, Promise>` 去重，避免详情页多个来源同时打开时重复请求。
- `autoFetch = false` 时只读缓存：未命中返回 `detailAvailable=false`，不访问站点；文件缺失/损坏只返回错误，不清索引/不抓取，等 `autoFetch=true` 时再修复。供离线/只读场景使用。
- 文件读取失败时，索引清空只影响该来源；不影响其它来源和列表数据。
- 演员/标签以 SQLite 的 `vod_actor` / `vod_class` 为准；详情文件里的 `actor` / `vodClass` 副本只用于自包含，不参与合并。
- 详情过期只影响 `detailStale` 标记，不影响已缓存的详情内容展示；是否刷新由调用方决定。
- 文件损坏/格式版本不支持时返回错误并记录 `FILE_CORRUPT`，清空索引后实时抓取；抓取失败则保留旧文件供排查，下次重试。
- 读取命中会限流更新 `detail_accessed_at`；未命中/损坏会清空索引并实时抓取，因此读接口可能写少量索引元数据，但不会改列表字段。

### 6.6 详情刷新

```text
videos:detail:refresh(videoId, { force? })
  ├─ 取该视频全部来源
  ├─ 对每个来源：
  │    索引缺失 / 文件不存在 / 解析失败 / detailStale / force
  │      → 加入待刷新列表
  ├─ 按站点分组，每批最多 10 个 sourceVideoId
  ├─ 请求 ac=detail&ids=...
  ├─ 解析 → 写详情文件（临时文件 + rename）
  ├─ 单批失败：返回该批错误，保留旧文件
  └─ 返回最新详情（重新走 6.5 读取）
```

- 同一视频的并发刷新用 `Map<videoId, Promise>` 去重，后到的调用复用进行中的 Promise。
- 列表同步只更新 SQLite 列表字段；发现 `source_ts` / `note` 与 `detail_source_ts` / `detail_note` 不一致时置 `detail_stale = 1`，不重写文件。
- `detail:refresh` 的目标：索引缺失、文件缺失/损坏、`detail_stale = 1`，或显式 `force = true`。
- 刷新失败写 `detail_error`，保留旧文件/旧索引；成功写文件并回填索引、清 `detail_error`/`detail_stale`。
- `videos:detail` 的自动抓取与 `detail:refresh` 共用同一套“抓取 → 写文件 → 回填索引”逻辑。

## 7. 唯一性、合并与主来源

### 7.1 唯一键

- 来源唯一键：`UNIQUE (site_id, source_video_id)`。
- 同一个站点、同一个视频 ID，多次采集只更新这一行，不会重复。
- `source_video_id` 全程字符串，18 位 ID 不转 Number；JSON 解析前对 `vod_id` / `id` 的 16 位以上纯数字加引号。

### 7.2 名字合并

- `name_key = NFKC(name).toLowerCase()`，去掉空白、全角空格、零宽字符。
- 例如：
  - `名侦探柯南` 与 `名侦探柯南 ` 合并；
  - `名侦探柯南（国语）` 与 `名侦探柯南(国语)` 合并（NFKC 全角转半角）；
  - `名侦探柯南 国语` 与 `名侦探柯南国语` 合并（去空白）。
- 不做别名、季数、清晰度、语言版本的模糊合并；需要时另加 `merge_key`，不要改 `name_key` 的精确语义。
- 名字为空的记录跳过；归一化后为空但原名非空时，用 trim 后的原名作为 key。

### 7.3 主来源

主来源 = 该视频所有来源中按以下顺序的第一条：

1. `source_ts DESC`（最近更新优先）；
2. `id ASC`（稳定兜底）。

列表只显示主来源的原始分类与绑定分类；详情页列出全部来源。这样列表不会因为合并而变成多行，也不会把不同站点的分类混在一行里。

> 因为 SQLite 不再记录详情状态，主来源选择不再使用“已有详情优先”作为 tie-break；如果主来源封面为空，重算时回退到第一个有封面的来源。

### 7.4 写入合并流程

单页采集在一个 SQLite 事务内完成：

1. 对每条记录算 `name_key`。
2. 按 `name_key` 查 `videos`，没有则插入占位行。
3. 按 `(site_id, source_video_id)` 查 `video_sources`：
   - 不存在：插入，指向第 2 步的规范视频；
   - 存在但 `video_id` 不同：来源改名，更新 `video_id`，旧规范视频加入待重算集合。
4. upsert 来源的列表字段：
   - `pic` / `note` 新值为空时保留旧值；
   - `vod_actor` / `vod_class` 新值为空时保留旧值，非空时更新；避免站点偶发不返回这两个字段时把已有演员/标签冲掉；
   - `full + all` 时把 `last_full_run` 写成本次运行 token（`collect_progress.started_at`），即使该行列表字段没有变化也要写，供本轮结束后找出“本次未返回”的旧来源；
   - 其它模式不改 `last_full_run`；
   - 已有详情索引且 `source_ts` / `note` 与 `detail_source_ts` / `detail_note` 不一致时，置 `detail_stale = 1`；不重写详情文件；
   - 不删除、不覆盖详情文件。
5. 对受影响的 `video_id` 重算：
   - 无来源 → 删除 `videos` 行（FTS 触发器同步删除）；
   - 有来源 → 重算主来源、`latest_ts`、`pic`、`note`、`vod_actor`、`vod_class`、`intro_excerpt`、`source_count`；
   - `name` / `search_text` 仅在真正变化时更新，避免无意义 FTS 重建。
6. 本页 upsert 一次 `cache_sites`（不是每行）。

## 8. 列表页

### 8.1 列表项字段

| 展示项 | 来源 |
|---|---|
| 视频名称 | `videos.name` |
| 预览图 | `videos.pic`（主来源，空值回退） |
| 更新进度 | `videos.note`，如“更新至第07集” |
| 原始分类 | 主来源 `video_sources.category_id` / `category_name` |
| 演员（可选） | `videos.vod_actor`（主来源优先，空值回退） |
| 标签（可选） | `videos.vod_class`（主来源优先，空值回退） |
| 绑定分类 | 读时按 `(site_id, source_id)` 反查 `category_bindings` |
| 介绍摘要 | `videos.intro_excerpt` + `intro_truncated` |
| 更新时间 | `videos.latest_time` / `latest_ts` |
| 来源数 | `videos.source_count` |

绑定分类查询：

```sql
SELECT sc.source_id, sc.name AS source_name,
       b.video_category_id, vc.name AS category_name, vc.parent_id, vc.visible
FROM site_categories sc
LEFT JOIN category_bindings b ON b.site_category_id = sc.id
LEFT JOIN video_categories vc ON vc.id = b.video_category_id
WHERE sc.site_id = ? AND sc.source_id IN (...);
```

- 未绑定：列表显示原始分类名。
- 已绑定：列表显示绑定后的本地分类完整路径。
- 绑定关系改变后不需要重采，下一次读取立即生效。
- 隐藏分类不在缓存层过滤，返回 `bound.visible`，由展示端按现有 `visible` 规则处理。

### 8.2 查询与分页

```sql
SELECT v.id, v.name, v.pic, v.note, v.intro_excerpt, v.intro_truncated,
       v.latest_ts, v.latest_time, v.source_count,
       v.vod_actor, v.vod_class,
       s.site_id, s.source_video_id, s.category_id, s.category_name
FROM videos v
JOIN video_sources s ON s.id = v.primary_source_id
WHERE 1 = 1
  -- 关键字：AND v.id IN (SELECT rowid FROM videos_fts WHERE videos_fts MATCH ?)
  -- 分类：AND EXISTS (SELECT 1 FROM video_sources f
  --        WHERE f.video_id = v.id
  --          AND ((f.site_id = ? AND f.category_id = ?) OR ...))
  -- 游标：AND (v.latest_ts < ? OR (v.latest_ts = ? AND v.id < ?))
ORDER BY v.latest_ts DESC, v.id DESC
LIMIT ?;  -- 多取 1 条判断 nextCursor
```

- 默认按 `latest_ts DESC, id DESC`，即更新时间倒序。
- 键集分页，不使用 `OFFSET`，百万级深翻页不衰减。
- 返回 `items` + `nextCursor`，**不返回 total**；需要总数时单独调 `videos:stats`，避免每次翻页 `COUNT(*)`。
- `limit` 默认 30，最大 100。

## 9. 搜索

- 只搜视频名称，不搜演员/导演/简介；后续需要再扩展。
- 走 FTS5，不使用 `LIKE '%词%'`。
- 查询构造：
  - `柯南` → `"柯 南"`
  - `复仇者联盟` → `"复 仇 者 联 盟"`
  - `spider` → `spider*`
  - `spider 蜘蛛` → `spider* "蜘 蛛"`
- 搜索词只有标点/空白 → 直接返回空列表，不退化成全表扫描。
- 结果仍按 `latest_ts DESC, id DESC` 排序；FTS 负责筛 ID，SQLite 负责排序和分页。

性能基线（Electron 44 / SQLite 3.53.4 实测）：

- 30 万条合成数据：FTS 查询约 10–20ms。
- `LIKE '%词%'` 无匹配时约 190ms（百万级约 0.6s），因此不采用。
- 百万级目标：搜索 p95 < 200ms；列表首页/游标页 < 100ms。

## 10. 采集与进度

### 10.1 请求参数

- 列表采集：`ac=detail&pg=N&pagesize=100`。
  - `ac=detail` 一次返回列表 + 封面 + 播放地址，避免“先 list 再按 ids 补封面”的两次请求。
  - 解析失败时可重试一次 `ac=videolist`（官方历史别名）。
  - `pagesize` 被站点忽略时，以响应回读的 `pagesize/limit` 为准。
- XML：`at=xml`；JSON：删除 `at`。
- 可选：`t` 分类、`wd` 关键词、`ids` 指定视频、`h` 最近 N 小时。
- 采集方式与请求参数：
  - `fetch_range=all`：不传 `h`，按全量分页翻。
  - `fetch_range=24h`：传 `h=24`，只取最近 24 小时更新。
  - `fetch_range=48h`：传 `h=48`，只取最近 48 小时更新。
- 来源扩展字段映射：
  - `vod_actor`：JSON 取 `vod_actor`，XML 取 `<actor>`；原样保存演员文本，截断到 1000 字。
  - `vod_class`：JSON 取 `vod_class`；XML 的 `<class>` 是分类列表，不是单视频标签，不要映射成 `vod_class`。截断到 500 字。
- 请求头与现有分类接口一致（Chrome UA、`Accept-Language: zh-CN`）；超时 20s；网络错误/429/5xx 重试 2 次。

### 10.2 列表采集循环

手动/定时触发后先进入全局单队列：

- 入队时 `status = queued`、`page = 0`、计数清零，写一条“已入队”日志。
- 队列空闲时取出任务，`status = running`、写 `started_at`，写“开始采集”日志。
- 同一 `(site_id, mode, fetch_range)` 已在运行/排队时不再重复入队。

队列取出后按页循环：

1. 检查站点存在、未取消。
2. 请求一页。
3. 解析 → 一个事务写列表数据。
4. 更新 `collect_progress`（`page`、`page_count`、`record_count`、`page_size`、`fetched`、`inserted`、`updated`、`failed`）。
5. 推送进度事件（主进程 → 渲染层）。
6. 每 10 页写一条进度日志（页/总页/计数），避免每页刷日志。
7. 让出事件循环，继续下一页。

结束条件：

- 到达 `pagecount`、空页、或达到 `maxPages`（full 默认 500 / incremental 默认 100）。
- `fetch_range=all`：按 `page_count` 翻完。
- `fetch_range=24h/48h`：请求时带了 `h=24/48`，按 `page_count` 翻完；不再依赖 `last_sync_at` 判断追平。
- `mode=incremental + fetch_range=all`：不推荐/建议禁止；如允许，等同全量翻页 + upsert，没有截止点。
- **`full + all` 的提前空页**：如果 `page < page_count` 就返回空列表，视为异常，记 `error = INCOMPLETE_PAGE`，不推进 `page`、不执行全量替换；下次重试当前页。
- `full + all` 只有处理到 `page >= page_count` 才算完整结束。
- 达到 `maxPages` 未完成 → `paused`，下次从下一页继续。

完成：

- `full + all`：先进入 `replacing`，按 10.4 完成全量替换后再置 `done`；
- 其它模式：直接 `status = done`，写 `finished_at`；`finished_at` 即“上次成功同步时间”；
- 写一条完成日志（页数、抓取/新增/更新/失败/删除数）；
- 每 10 页做一次 FTS `merge`，控制索引段数量；
- 结束后 `PRAGMA wal_checkpoint(PASSIVE)` + `PRAGMA shrink_memory`，归还页缓存。

取消/错误：

- 取消 → `paused`，已提交页保留，写 `warn` 日志。
- 错误 → `error`，`page` 停在最后一次成功页，下次重试当前页，写 `error` 日志。
- 站点被删除 → 下一页前检测并停止。

### 10.3 详情采集

- 列表采集不写详情文件；详情文件由 `videos:detail` 未命中实时抓取，或由 `detail:refresh` 主动刷新产生。
- 按 `ids` 批量请求，每批最多 10 个，避免 URL 过长。
- 每个来源单独写文件，并回填 `video_sources.detail_*` 索引。
- 单批失败只影响该批，写 `detail_error`，不清空已有详情文件/索引里的旧值。

### 10.4 `full + all` 全量替换

目标：整轮全量采集**成功完成后**，让该站点在 `video_sources` 中的来源集合等于本次完整返回的集合；本次未返回的旧来源删除。

核心约束：

- 只在整个 `full + all` 任务成功完成后替换；未完成、暂停、取消、错误、达到 `maxPages` 都不删除。
- 用运行 token 标记本次看到的来源；token 持久化，可跨重启续采。
- 删除旧来源后，重算合并视频，并删除对应的详情文件。

#### 10.4.1 运行 token 与标记

- `runToken = collect_progress.started_at`（新任务生成，续采保持不变；`restart` 重新生成）。
- 新 run 的判定：上次 `status = done`、或显式 `restart = true`、或该组合还没有进度行；此时生成新的 `started_at`、`deleted = 0`。`paused` / `error` / `replacing` 续采沿用原 `started_at`。
- `runStartTs = Date.parse(started_at)`，用于删除条件；`started_at` 无效时回退到本次任务第一次写入进度的时间。
- `full + all` 每页 upsert 时，无论列表字段是否变化，都把 `video_sources.last_full_run = runToken`。
  - 如果列表字段的 upsert 用了 `WHERE` 跳过“值未变化”的行，`full + all` 必须额外执行 `UPDATE video_sources SET last_full_run = ? WHERE site_id = ? AND source_video_id = ?`，不能依赖列表字段是否变化。
  - 这会让 `full + all` 每行至少写一次；`last_full_run` 上的索引会增加写放大，但换来确定性，可接受。
- 其它模式（`incremental + 24h/48h`，以及被禁止的 `incremental + all`）**不改** `last_full_run`。
- 来源由非全量模式新增时，`last_full_run = ''`，下一次 `full + all` 会重新标记。

#### 10.4.2 替换前提（必须全部满足）

- `mode = full` 且 `fetch_range = all`；
- 已处理到 `page_count`（`page >= page_count`），或站点明确返回 `page_count = 0` 且允许空站点；
- 本轮没有 `error`、没有被取消、没有因 `maxPages` 暂停；
- `fetched > 0`，除非调用方显式传 `allowEmpty = true`；
- 站点返回了可靠的 `page_count` / `record_count`；如果分页字段缺失，跳过替换并记录 warning，避免误删。

任一条件不满足：只保留 upsert 结果，不执行删除；`status = done`，`error` 写入警告（如 `REPLACE_SKIPPED_EMPTY` / `REPLACE_SKIPPED_PAGE_COUNT` / `REPLACE_SKIPPED_FAILED`），让调用方知道“采集完成但未替换”，不要把任务误标为失败。

#### 10.4.3 替换步骤

1. `status = replacing`；新运行开始时 `deleted = 0`，续采/续清理保留已累计值。
2. 分批（例如 1000 行）查询待删除的旧来源：

```sql
SELECT id, source_video_id, video_id
FROM video_sources
WHERE site_id = ?
  AND last_full_run <> ?
  AND source_ts <= ?          -- runStartTs，见 10.4.4
LIMIT 1000;
```

3. 记录这批 `source_video_id`（用于删详情文件）和 `video_id`（放入待重算集合/临时表）。
4. 删除这批来源行。
5. 重复 2–4，直到没有待删除行。
6. 对受影响的 `video_id` 重算合并视频；没有来源的 `videos` 删除（FTS 触发器同步删除）。
7. 按 `siteId + sourceVideoId` 推导详情文件路径，删除这些来源的详情文件（尽力而为；失败留孤儿文件）。
8. `deleted = 累计删除行数`；`status = done`；写 `finished_at`。

#### 10.4.4 并发与分页安全

采集期间站点可能新增/更新数据，导致按时间倒序的分页发生位移。删除条件加：

```sql
source_ts <= runStartTs
```

- 本次没看到、且 `source_ts` **晚于**运行开始时间：可能是运行期间新更新/插入的数据，保留，下一次全量再处理。
- 本次没看到、且 `source_ts` **早于或等于**运行开始时间：认为确实已下架，删除。
- 站点分页/总页数不可靠时，不启用全量替换，只做 upsert；宁可留旧数据，也不误删。

#### 10.4.5 中断恢复

- 进度在 `page_count` 之前：只 upsert，不删除。
- 崩溃在 `replacing` 阶段：
  - 状态仍为 `replacing`；
  - 下次 `start` 检测到 `page >= page_count` 且 `status = replacing`，继续从第 2 步清理；
  - 已删除的行不会再次出现，`deleted` 继续累加，不需要重置。
- `deleted` 只在新 run（`started_at` 变化）时清零；暂停续采、`replacing` 续清理都保留。

#### 10.4.6 空站点保护

- `fetched = 0` 时默认**不替换**，避免站点临时返回空把缓存清空。
- 只有调用方显式传 `allowEmpty = true`，才允许在 `fetched = 0`、`page_count = 0` 时删除该站点全部来源。
- `page_count` 缺失、`record_count > 0` 但列表为空等异常：跳过替换，记录 `error`/warning。

#### 10.4.7 对合并视频与详情文件的影响

- 删除来源后，某个 `videos` 可能只剩一个或零个来源：
  - 有来源：重算主来源、`latest_ts`、`pic`、`note`、`vod_actor`、`vod_class`、`intro_excerpt`、`source_count`；
  - 零来源：删除 `videos` 行，FTS 同步删除。
- 主来源被删时，列表封面/进度自动切到新的主来源。
- 只删除被删来源自己的详情文件；保留来源的详情文件不动。
- 详情文件删除失败只留下孤儿文件，不影响数据正确性；由 `videos:capacity:scan` / 维护任务清理。

## 11. 一致性与写入顺序

SQLite 和文件系统没有跨介质事务，但两者职责已经分开：列表只写 SQLite，详情只写文件。因此不存在“详情文件和 SQLite 详情元数据不一致”的问题。

### 11.1 列表写入

- 一页一个 SQLite 事务；失败整页回滚。
- 进度在事务提交后更新；若崩溃，最多重采一页，upsert 幂等。
- `full + all` 的全量替换清理分批进行（见 10.4），每批一个事务；中断后按 `replacing` 状态续清理，不重复计数。

### 11.2 详情写入

1. 请求详情。
2. 写临时文件 → rename。
3. 更新 `video_sources` 的 `detail_path / detail_size / detail_cached_at / detail_accessed_at / detail_source_ts / detail_note / detail_stale / detail_error`。
4. 失败处理：
   - 临时文件写失败：旧文件/旧索引保留，写 `detail_error`，返回 `FILE_WRITE_FAILED`；
   - rename 失败：同上；
   - 索引更新失败：文件可能已覆盖，但索引仍是旧值；下次读取按索引校验，发现不匹配会重新抓取，容量扫描可清理孤儿；
   - 进程崩溃在 rename 与索引更新之间：文件是新内容、索引是旧状态；读取时以文件校验为准，必要时重新抓取并回填。

详情写入不再是“只写文件”，而是“文件 + 索引”两步；两步之间允许短暂不一致，但读取路径会校验并自愈。

### 11.3 删除站点 / 清空缓存

删除站点：

1. 取消该站点采集/排队任务。
2. 删除该站点的 `video_sources`、`collect_progress`、`cache_sites` 行。
3. `collect_schedules` 通过业务库外键 `ON DELETE CASCADE` 一并删除。
4. 重算受影响 `videos`，删除空规范视频（FTS 触发器同步）。
5. 删除 `Data/videos/<siteId>/` 目录（尽力而为；失败留孤儿文件，后续维护清理）。
6. `collect_logs` 保留，便于回看删除前的运行记录；界面把找不到站点的日志显示为“已删除站点”。

清空缓存：

1. 取消全部采集和详情刷新，清空内存队列，递增 `cacheEpoch`，阻止在途写回。
2. 关闭缓存库 SQLite 连接。
3. 删除 `video-cache.db`、`-wal`、`-shm`。
4. 删除 `Data/videos/` 目录。
5. 重新打开数据库、建表/索引/触发器。
6. `collect_progress` / `collect_logs` 随缓存库一起清空；`collect_schedules` 在业务库中保留。
7. 删除失败时回退到分批 `DELETE` + checkpoint，并返回错误原因。

`cacheEpoch` 的作用：清空/删站点开始后，旧的详情文件写入即使完成，也不能再 rename 到目标路径；写入方在写临时文件前后检查 epoch 和站点是否仍存在，发现变化就删除临时文件并放弃。

## 12. 内存、启动与磁盘

### 12.1 打开数据库不会把库读进内存

- SQLite 按需分页：打开 `video-cache.db` 只读元数据/页头，不加载全表、不加载 FTS 索引。
- FTS5 索引在磁盘上，查询只读相关页。
- 详情文件只在打开某个详情页时读取，启动时不遍历 `Data/videos`。
- 详情索引只是 `video_sources` 上的短文本/整数字段，随列表行读取；不会因为详情正文大而增加启动内存。
- 容量统计默认走索引聚合，不遍历详情目录。
- 1GB 缓存库不等于启动占 1GB 内存；常规启动增量主要是 SQLite 连接、页缓存和少量 schema 页。

### 12.2 连接参数上限

```sql
PRAGMA cache_size = -32768;           -- 32 MiB 页缓存上限，按需增长
PRAGMA mmap_size = 67108864;          -- 64 MiB 虚拟映射，按需驻留
PRAGMA journal_size_limit = 67108864; -- 单次 WAL 上限
PRAGMA wal_autocheckpoint = 1000;
```

- 不使用 `PRAGMA temp_store = MEMORY`，避免大排序把内存拉高。
- 参数是常量，后续可按实测调低到 16/32 MiB。

### 12.3 启动阶段

`video-cache-store.init()` 只做：

1. 打开文件，设置 PRAGMA。
2. `CREATE TABLE / INDEX / VIRTUAL TABLE / TRIGGER IF NOT EXISTS`。
3. 读 `PRAGMA user_version`；只有版本 0 且已有数据的迁移场景才重建 FTS。
4. 读 `cache_sites`（每站点一行）与 `sites` 对账；通常无差异。

启动阶段不做：

- `COUNT(*)`；
- `SELECT DISTINCT site_id FROM video_sources`；
- FTS `optimize/rebuild`；
- 遍历 `Data/videos`；
- 读取任何详情文件。

调度器与日志的启动工作：

- `collect-scheduler` 只读 `collect_schedules`（每站点一行），不扫描视频表；把遗留的 `queued` 进度重置为 `idle`，到期的计划补跑一次。
- `collect_logs` 启动时按保留策略裁剪一次（最多 5000 行/30 天），走 `created_at` 索引。

### 12.4 详情读取的内存边界

- 单个详情文件最大 2 MiB。
- 一个合并视频通常 1–3 个来源，极端情况几十个；按来源顺序读取、解析，结果对象保留。
- 最坏情况 20 个来源 × 2 MiB ≈ 40 MiB，属于可接受上限；正常远低于此。
- 文件读取用异步 I/O，避免阻塞主进程；JSON 解析在主进程完成，2 MiB 级别耗时为毫秒级。

### 12.5 容量估算

- SQLite 列表缓存：100 万视频 + 100 万来源约 0.3–0.5GB（含 FTS 和索引）。
- 详情文件：只统计看过的视频，单个约 10–100KB；1 万个详情约 0.1–1GB。
- 详情文件数量/总大小默认由索引统计（`COUNT(*)`、`SUM(detail_size)`），不扫目录；需要和文件系统对账时再按需扫描（见 15.1）。
- 磁盘不足时优先清理详情文件或整体清空缓存。

## 13. 失败模式与边界

| 场景 | 处理 |
|---|---|
| 同站点同视频 ID 重复抓取 | `(site_id, source_video_id)` upsert，不重复 |
| 来源改名 | 迁移到新 `name_key` 的规范视频；旧规范视频无来源则删除 |
| 同名不同站 | 合并到一个 `videos`，多个来源 |
| 同名同站不同 ID | 也合并，详情列出多个来源 |
| 站点删除 / 恢复备份 | 取消采集、删来源/进度/`cache_sites`、删站点详情目录、重算空视频 |
| 站点地址/格式变化 | 清空该站点缓存与详情目录 |
| 详情文件不存在 | 索引未命中；`autoFetch=true` 时实时抓取并回填，`false` 时 `detailAvailable=false` |
| 索引有但文件缺失 | 清空该来源索引 → 实时抓取 → 回填；失败记 `FILE_MISSING` |
| 详情文件损坏/格式不符 | `detailError=FILE_CORRUPT`，清空索引 → 抓取重写；不覆盖旧文件 |
| 详情文件过大 | `detailError=TOO_LARGE`，保留列表数据 |
| 详情写入时进程崩溃 | 文件/索引可能短暂不一致；读取校验后自愈；容量扫描可对账 |
| 清理详情缓存时文件被占用 | 返回部分失败/警告；索引仍重置，避免指向坏文件 |
| 采集失败/断网/超时 | 重试 2 次；仍失败记 `error`，停在上一次成功页 |
| `full + all` 未完整结束 | 暂停/取消/错误/达到 `maxPages` 时不删除旧来源，保留 upsert 结果 |
| `full + all` 提前空页（`page < page_count`） | 记 `INCOMPLETE_PAGE`，不替换，下次重试当前页 |
| `full + all` 运行期间出现新数据 | `source_ts > runStartTs` 的未返回来源保留，下一次全量再处理 |
| `full + all` 站点临时返回空 | `fetched = 0` 默认不替换；只有 `allowEmpty = true` 才清空该站点来源 |
| `full + all` 分页字段缺失 | 跳过全量替换，只做 upsert，记录 warning |
| `full + all` 在 `replacing` 阶段崩溃 | 状态保留 `replacing`，下次启动继续清理，`deleted` 继续累加 |
| 应用退出 | 取消运行中采集、清空内存队列，checkpoint，关闭 DB；遗留 `queued` 下次启动重置为 `idle` |
| 定时到点但队列忙 | 跳过本次并写 `warn` 日志，仍推进 `next_run_at`，避免每 30 秒重试 |
| 定时计划在停机期间过期 | 启动时只补跑一次，然后把 `next_run_at` 推到 `now + interval` |
| 日志写入失败 | 不影响采集主流程；只记录到控制台/内存，不因日志失败中断采集 |
| 站点返回 `closed` / 鉴权文本 | `CLOSED` / `AUTH`，不写缓存 |
| 分页字段缺失 | 以实际返回条数和空页判断结束 |
| `pagesize` 被忽略 | 以回读值为准 |
| 18 位视频 ID | 全程字符串；JSON 大整数加引号 |
| 简介含 HTML | 写入前转纯文本；渲染层按文本展示 |
| 封面相对路径 / `//` | 按站点地址补全；无法补全存空串 |
| 缓存库初始化失败 | 不阻塞应用启动；`videos:*` 返回 `CACHE_UNAVAILABLE` |
| 清空时文件被占用 | 回退分批 DELETE + checkpoint；仍失败返回错误 |
| 搜索词只有标点 | 返回空列表，不全表扫描 |
| FTS 语法错误 | 构造阶段过滤；兜底捕获 |

## 14. 安全

- 路径安全：`siteId` 校验；`sourceVideoId` 白名单或哈希；推导出的路径拼 root 后 `resolve` 校验前缀；拒绝 `..`、绝对路径、盘符。
- 文件读取前 `lstat`，拒绝符号链接（本地缓存，防御性措施）。
- 详情 JSON 只白名单读取已知字段，不把对象直接合并进原型。
- 简介是纯文本；渲染层禁止 `dangerouslySetInnerHTML`。
- 播放地址原样保存，但只允许 `http/https` 用于播放/打开；缓存层不发起请求。
- 单文件大小、简介长度、分集数量都有上限，避免磁盘/内存被单条数据打爆。
- 缓存目录默认权限，不存放任何账号/令牌。

## 15. 清理、统计与备份

### 15.1 容量统计（`videos:capacity`）

容量页默认只读 SQLite 索引和文件 `stat`，不遍历详情目录：

| 指标 | 来源 |
|---|---|
| `dbBytes` | `video-cache.db` + `-wal` + `-shm` 的 `stat` 大小 |
| `videoCount` / `sourceCount` | `videos` / `video_sources` 行数 |
| `detailCount` | `COUNT(*) WHERE detail_cached_at <> ''` |
| `detailBytes` | `SUM(detail_size) WHERE detail_cached_at <> ''` |
| `logCount` | `collect_logs` 行数 |
| `siteCount` | `cache_sites` 行数 |
| `lastCollectedAt` | `MAX(finished_at)`（done 状态） |
| `sites[]` | 按站点 `GROUP BY site_id` 的 `detailCount` / `detailBytes`，用于容量页展开 |

- `detailCount` / `detailBytes` 走 `idx_video_sources_detail` 部分索引，不扫目录，也不受详情文件数量影响。
- `videos:stats` 仍可保留基础计数；容量页优先用 `videos:capacity`。

需要和文件系统对账时，单独调用：

- `videos:capacity:scan`：递归扫描 `Data/videos`，统计 `.json` 数量、总字节、`.tmp-*` 孤儿数量；与索引对比后返回差异，可选把“索引有、文件缺失”的行清空索引。
- 只在容量页点“重新扫描/校对”时运行，可带进度/取消；不放进启动路径。

### 15.2 清理详情缓存（`videos:details:clear`）

- 支持 `{ siteId? }`：传站点只清该站点，不传清全部详情。
- 删除 `Data/videos/<siteId>` 或整个 `Data/videos` 目录；删除前统计字节数用于返回 `freedBytes`。
- 把对应行的 `detail_path / detail_size / detail_cached_at / detail_accessed_at / detail_source_ts / detail_note / detail_stale / detail_error` 重置为空/0；更新 `detail_path <> ''` 或 `detail_cached_at <> ''` 的行，分批执行，避免长事务。
- **保留** `videos` / `video_sources` 列表数据、搜索索引、采集进度、日志和定时计划；清完后详情页再次打开会走“索引未命中 → 实时抓取 → 回填”。
- 文件删除失败只留下孤儿文件并返回警告；索引仍会被重置，避免指向不存在的文件。

### 15.3 清理全部缓存（`videos:clear`）

- 取消采集/详情刷新，清空内存采集队列，递增 `cacheEpoch`。
- 删除 SQLite 缓存库与 `Data/videos`；`collect_progress`、`collect_logs` 一并清空。
- 重建空缓存库。
- `collect_schedules` 在业务库中，**不受影响**；清空后如果计划到期，调度器会正常重新入队。
- 返回释放的字节数：SQLite 页面总数 × 页大小 + 删除前扫描到的详情文件总字节。

### 15.4 备份

- 备份包含五张业务表：`sites`、`site_categories`、`video_categories`、`category_bindings`、`collect_schedules`。
- `collect_schedules` 是用户配置，必须随备份走；`backup-store` 已增加 `schedules` 计数、`readState` / `parseBackup` / `applyState`，并兼容旧备份没有该表的情况（备份版本已升到 2，版本 1 按空计划恢复）。
- `video-cache.db` 和 `Data/videos` **不进备份**：它们是可重建缓存，避免备份文件被百万视频撑爆；`collect_logs` 同样不进备份。
- 恢复备份后：
  - 按 `cache_sites` 对账，删除已不存在的站点缓存；
  - 地址/格式变化的站点清空缓存；
  - 站点 ID 与地址都未变的缓存可以保留；
  - 计划随业务库恢复；如果计划里的站点在备份中不存在，外键/校验会拒绝该行，恢复前应整体校验。

## 16. 控制台：采集、进度、容量与日志

控制台从“只有站点/分类/备份可用”扩展到完整的采集入口：新增「采集」「进度」「容量」，移除原来的「任务」占位，「日志」接真实采集日志。

### 16.1 导航调整

现有导航：

```text
概览 / 站点 / 分类 / 备份 / 任务 / 日志
```

调整为：

```text
概览 / 站点 / 分类 / 采集 / 进度 / 容量 / 备份 / 日志
```

- 移除「任务」：它原本只是空状态占位，实际运行信息由「进度」承担。
- 新增「采集」：手动采集入口 + 定时采集设置。
- 新增「进度」：按站点显示采集进度、状态、计数和错误。
- 新增「容量」：显示 SQLite 缓存与详情文件缓存体积，支持手动清理。
- 「日志」从占位改为读取 `collect_logs`，实时显示采集日志。
- `Console.tsx` 的 `ConsoleSection`、`NAV_ITEMS`、`SECTION_META` 同步调整；新增 `Collect.tsx`、`Progress.tsx`、`Capacity.tsx`、`Logs.tsx` 四个面板。

### 16.2 采集分区

「采集」分区以站点为单位展示：

| 信息 | 说明 |
|---|---|
| 站点名 | `sites.display || sites.name`，与站点页一致 |
| 格式 | XML / JSON |
| 当前状态 | `idle / queued / running / paused / replacing / error`，来自 `collect_progress` |
| 上次采集 | `finished_at` / `updated_at` |
| 下次计划 | `collect_schedules.next_run_at`，未启用显示“未启用” |
| 操作 | 立即采集、定时设置、取消、查看进度 |

手动采集弹窗：

- 模式：增量 / 全量（`mode`）。
- 采集方式：全量 / 24 小时内 / 48 小时内（`fetch_range`）。
- 高级：`allowEmpty`（只在 `full + all` 且确实要清空空站点时勾选，默认关闭）。
- 提交后调用 `videos:collect:start`；如果同一组合已在运行/排队，提示“已在队列中”，不重复入队。

定时设置弹窗：

- 开关：启用 / 关闭。
- 间隔：30 分钟、1 小时、3 小时、6 小时、12 小时、24 小时，或自定义分钟数（最小 5）。
- 模式 / 采集方式：与手动采集一致。
- 保存后显示“下次运行时间”；关闭时清空 `next_run_at`。

手动和定时共用同一个采集队列，不会因为同时点两次而跑两个任务。

### 16.3 定时调度

- 调度器在主进程 `collect-scheduler.ts`，只做“到点入队”，不直接做网络/写库。
- 每 30 秒 tick 一次，查询：

```sql
SELECT * FROM collect_schedules
WHERE enabled = 1
  AND next_run_at <> ''
  AND next_run_at <= ?   -- 当前 UTC ISO
ORDER BY next_run_at ASC;
```

- 命中后调用采集器 `enqueue(siteId, mode, fetchRange, 'schedule')`，并把 `last_run_at = now`、`next_run_at = now + interval_minutes`。
- 同一 `(site_id, mode, fetch_range)` 已在运行/排队：跳过本次触发，写一条 `warn` 日志，但仍然推进 `next_run_at`，避免每 30 秒重复尝试。
- 应用启动时补跑一次：如果 `next_run_at` 已过期，入队一次，然后把 `next_run_at` 推到 `now + interval`；不连续补跑停机期间的多次。
- 应用退出：清掉定时器；运行中的采集按现有逻辑取消/暂停；计划和 `next_run_at` 已落库，下次启动继续。
- 站点地址/格式修改：计划保留，下次触发使用新地址；站点删除：`collect_schedules` 通过外键级联删除。
- 时间统一存 ISO 8601 UTC，界面按本地时区展示。

### 16.4 进度分区

「进度」分区按站点展示 `collect_progress` 的当前/最后一次运行：

| 列 | 来源 |
|---|---|
| 站点 | `collect_progress.site_id` + `sites` 显示名 |
| 模式 | `mode`（增量/全量） |
| 采集方式 | `fetch_range`（全量/24h/48h） |
| 状态 | `status`，带颜色标签 |
| 进度 | `page / page_count`，计算百分比；`page_count = 0` 时显示不确定进度 |
| 抓取 / 新增 / 更新 / 失败 / 删除 | `fetched / inserted / updated / failed / deleted` |
| 时间 | `started_at / finished_at / updated_at` |
| 错误 | `error`，悬停或展开看全文 |

行为：

- 按站点分组；同一站点有多个模式/采集方式时显示多行。
- `running` / `replacing` 排在最前；`queued` 显示“排队中”；`idle` 可以显示“未采集”。
- 通过 `videos:collect:progress` 事件实时更新，不要求用户手动刷新。
- 行内操作：取消（`queued` 直接移出队列，`running` 转 `paused`）、查看该站点日志、跳转「采集」重新发起。
- 没有采集记录时显示空状态“还没有采集记录，去「采集」发起一次”。

### 16.5 容量分区

「容量」分区显示两类缓存并支持手动清理：

| 区块 | 内容 |
|---|---|
| SQLite 缓存 | `video-cache.db` + `-wal` + `-shm` 大小；视频数、来源数、详情索引数、日志数 |
| 文件缓存 | 详情文件数量、总字节；按站点的详情数量/字节（可展开） |
| 总计 | SQLite + 详情文件合计 |

操作：

- **刷新**：调用 `videos:capacity`，只读索引与 `stat`，通常很快。
- **扫描校对**：调用 `videos:capacity:scan`，遍历 `Data/videos` 统计真实文件数/字节，和索引对比；可清理“索引有、文件不存在”的行和 `.tmp-*` 孤儿。只在用户点击时运行。
- **清理详情缓存**：调用 `videos:details:clear`，可选择全部或单个站点；删除详情文件并重置详情索引，保留列表/搜索/进度/计划。确认弹窗显示预计释放字节。
- **清理全部缓存**：调用 `videos:clear`，重建缓存库并删除详情目录；保留业务库和定时计划。确认弹窗明确提示“列表、搜索、进度、日志会一起清空”。

交互：

- 清理前必须二次确认；执行中按钮 loading，完成后刷新容量数字并提示释放了多少字节。
- 文件删除失败时提示“部分文件被占用”，索引仍重置，避免详情页继续指向坏文件。
- 容量页不自动扫描目录；默认数字来自 `detail_size` 索引，和真实文件可能短暂有偏差，用“扫描校对”修正。

### 16.6 日志分区

「日志」分区读取 `collect_logs`：

- 工具栏：站点筛选、级别筛选（全部 / info / warn / error）、自动滚动开关、刷新、清空。
- 列表：时间、级别标签、站点、模式/采集方式、消息；错误详情可展开。
- 实时：订阅 `videos:logs:onAppend`，新日志追加到列表尾部；自动滚动默认开启。
- 分页：向上翻历史用 `beforeId` 游标，单页 100 条；客户端最多保留 1000 条，避免长时间运行内存膨胀。
- 清空：`videos:logs:clear` 支持按站点清空或全部清空，操作前确认。
- `videos:clear` 重建缓存库时日志也会清空；计划在业务库中不受影响。

### 16.7 采集队列与状态

- 全局单队列：同一时间只跑一个采集任务，避免网络/写库竞争。
- 队列：内存 FIFO；手动和定时都调用 `enqueue`，按 `(site_id, mode, fetch_range)` 去重。
- 入队后 `collect_progress.status = queued`，`page = 0`，计数清零；真正开始执行时置 `running` 并写 `started_at`。
- 取消：
  - `queued`：从队列移除，状态回 `idle`；
  - `running`：中止当前请求，状态 `paused`，保留已提交页；
  - `replacing`：中止清理，状态 `paused`，下次继续替换（见 10.4）。
- 应用退出：取消运行中任务、清空内存队列；下次启动把所有遗留 `queued` 重置为 `idle`，到期的计划会重新入队。
- 队列变化、开始、完成、取消都写 `collect_logs`，并通过 `videos:collect:progress` 推送状态。

| `videos:logs:list` | `{ siteId?, level?, beforeId?, limit? }` | `{ ok, logs: VideoCollectLog[], error? }` |
| `videos:logs:clear` | `{ siteId? }` | `{ ok }` |
| `videos:clear` | — | `{ ok, freedBytes?, error? }` |
| `videos:collect:progress` | 主进程 → 渲染层事件 | `VideosCollectProgress` |
| `videos:logs:onAppend` | 主进程 → 渲染层事件 | `VideoCollectLog` |

错误码建议：

`CACHE_UNAVAILABLE | DB | INVALID_INPUT | NOT_FOUND | BUSY | ALREADY_QUEUED | NETWORK | HTTP | PARSE | CLOSED | AUTH | FILE_CORRUPT | TOO_LARGE | FILE_WRITE_FAILED | FILE_DELETE_FAILED`

详情返回的每个来源包含 SQLite 的 `vodActor` / `vodClass`，以及详情索引字段（读取时会校验文件是否真的存在）：

- `detailAvailable`：该来源是否有可用详情文件；
- `detailStale`：索引标记的来源更新过（`detail_stale`）；
- `detailCachedAt`：索引里的详情缓存时间；
- `detailSize`：索引里的文件大小；
- `detailAccessedAt`：最近一次读取时间；
- `detailError`：最近一次抓取/读写错误，空表示正常。

## 18. 性能与验证方法

### 18.1 性能目标

- 百万级视频：搜索 p95 < 200ms；列表首页/游标页 < 100ms。
- 单页 100 条列表写入 < 200ms。
- 单个详情文件读取/解析 < 10ms（2 MiB 上限内）。
- `full + all` 全量替换：按 1000 行一批删除/重算，单批 < 200ms；不一次性加载全站来源到内存。
- 容量统计 `videos:capacity` < 20ms（索引聚合）；目录扫描只在手动点击时执行。
- 启动 100 万行缓存库：无全表扫描、无 FTS rebuild、无详情目录遍历、无明显内存尖峰。

### 18.2 验证方法

1. **SQLite 基准（临时脚本）**
   - 用 Electron 的 `ELECTRON_RUN_AS_NODE=1` + `node:sqlite`，按同一 schema 灌 20 万 / 100 万条；
   - `EXPLAIN QUERY PLAN` 确认 `videos_fts` 和 `idx_videos_latest` 生效；
   - 测 1 字、2 字、3+ 字中文与拉丁前缀查询。
2. **启动内存冒烟**
   - 灌 100 万行后关闭进程，重新启动，记录主进程 working set；
   - 对比空缓存启动；确认启动只读 `cache_sites`，不遍历 `Data/videos`。
3. **详情文件冒烟**
   - 构造 10KB / 1MB / 2MB / 超 2MB 的详情，验证写入、读取、截断、`TOO_LARGE`；
   - 删除文件、改坏 JSON，验证 `autoFetch=true` 时自动抓取回填，`autoFetch=false` 时 `detailAvailable=false` / `FILE_CORRUPT`；
   - 修改 SQLite 列表的 `source_ts`/`note`，验证读取时 `detailStale=true`；
   - 模拟进程在 rename 前退出，验证 `.tmp-*` 孤儿不影响读取。
4. **功能验收**
   - 两个站点同名视频：`videos` 1 行、`video_sources` 2 行；列表 1 条、详情 2 个来源。
   - 两站 `vod_actor` / `vod_class` 不同：`videos` 显示主来源聚合值；主来源为空时回退到其它来源；详情各来源显示自己的值。
   - 重复采集不增加来源；改名后旧规范视频删除、搜索旧名无结果。
   - 分类筛选/绑定变更即时生效。
   - 采集取消后从下一页续采。
   - `full + all` 完整跑完：本次未返回的旧来源被删除，`deleted` 计数正确，对应详情文件被删除。
   - `full + all` 在暂停/取消/错误/达到 `maxPages` 时：不删除旧来源。
   - 站点临时返回空且 `allowEmpty=false`：不删除旧来源；`allowEmpty=true` 才清空。
   - 运行期间新更新、`source_ts > runStartTs` 的来源即使本次未看到也保留。
   - `full + all` 在 `replacing` 阶段中断后再次启动：继续清理，不重复计数。
   - 控制台导航移除「任务」，包含「采集」「进度」「容量」「日志」。
   - 详情首次打开：索引为空 → 实时抓取 → 写文件 + 回填索引；第二次打开不再请求站点。
   - 删除详情文件后再次打开：识别为缺失 → 清索引 → 重新抓取 → 回填；列表数据不受影响。
   - `videos:details:clear` 后详情索引清空、文件目录清理，列表/搜索仍在；详情再次打开可重新抓取。
   - 容量页显示 SQLite/详情文件体积；`videos:capacity:scan` 能发现索引与真实文件差异。
   - 手动采集：入队 `queued` → `running` → `done`，进度实时刷新；取消 `queued` 回到 `idle`，取消 `running` 转 `paused`。
   - 定时采集：到点入队；队列忙时跳过并写 `warn`；停机后启动只补跑一次。
   - 日志：采集开始/每 10 页/完成/错误实时出现在「日志」，站点/级别筛选和清空可用。
   - `videos:clear` 后进度/日志清空，定时计划仍在业务库中。
   - `videos:clear` 后 SQLite 为空、详情目录为空、搜索为空。

## 19. 待确认问题

### 19.1 采集进度

已确认：

- 主键用 `site_id + mode + fetch_range`。
- 这张表只保留“当前进度/最后一次运行”，不保留每次采集历史。
- `full + all` 需要全量替换。

剩余待确认：

1. **`incremental + all` 是否允许**：本文不推荐/建议禁止，因为没有截止时间会退化成全量翻页。如果必须支持，需要恢复 `last_sync_at`（或单独加同步状态表）作为“追平”截止点。
2. **空站点保护**：`fetched = 0` 时默认不替换，只有显式 `allowEmpty = true` 才清空该站点来源。是否接受这个默认？
3. **删除条件**：全量替换只删 `source_ts <= runStartTs` 的未返回来源，避免删掉运行期间新更新的数据。是否接受？
4. **分页可靠性**：站点不返回可靠 `page_count`/`record_count` 时跳过全量替换，只做 upsert。是否接受？
5. **全量替换的详情文件**：删除旧来源时同时删除其详情文件（尽力而为，失败留孤儿）。是否接受？

### 19.2 详情与缓存

6. **详情文件粒度**：本文按“一个来源一个文件”设计（`siteId/sourceVideoId.json`）。是否接受？如果希望“一个合并视频一个文件”，需要把详情按来源合并写入，更新时要读改写。
7. **详情刷新策略**：索引未命中/文件丢失会自动抓取；`detail_stale = 1` 只在 `detail:refresh` 时刷新。是否需要在打开详情页时自动刷新过期详情？
8. **详情文件是否压缩**：当前用明文 `.json`，便于排查；如果详情文件数量/体积很大，是否改为 `.json.gz`？
9. **目录分片**：当前按站点一层目录；单站点详情文件超过十万时是否按哈希前缀分片？
10. **清理策略**：当前手动清理详情缓存（`videos:details:clear`）或全部缓存（`videos:clear`）。是否需要按容量/时间自动淘汰详情文件？
11. **搜索范围**：当前只搜名称。是否需要后续加演员、导演、简介？
12. **全量采集带宽**：列表采集用 `ac=detail` 一次拿全字段（含 `dl`），但只存列表字段。是否接受这个带宽换一次请求？如果站点响应过大，是否改为 `ac=list` + 分批补封面/简介？
13. **缓存上限**：是否需要设置缓存总量上限（例如 2GB）并在超限时提示/清理？
14. **详情统计**：容量页默认用索引统计；是否需要定期自动扫描校对索引与真实文件？

### 19.3 控制台与定时

15. **计划粒度**：当前每个站点一条计划。是否需要同一站点多条计划（例如 24h 每小时 + 全量每周）？如果要多条，`collect_schedules` 主键改为 `id`，并加 `UNIQUE (site_id, mode, fetch_range)`。
16. **调度表达**：当前用固定间隔分钟数（最小 5）。是否需要“每天固定时间”“每周几”或 cron？
17. **日志保留**：当前最多 5000 行/30 天。是否调整？
18. **日志与清空缓存**：当前 `videos:clear` 会清空日志和进度，但保留计划。是否希望日志保留更久、清缓存不动日志？
19. **计划备份**：当前计划随业务库备份。是否需要在恢复后自动恢复计划并重新计算 `next_run_at`？
